5 Mistakes Every Dev Makes
with setProperties

setProperties and applyPatches look simple on the surface, but hide traps that cause race conditions, silent data loss, and performance bottlenecks in production. Here are the 5 most common mistakes - and exactly how to fix them.

Why it matters

The API everyone uses, but few truly understand

setProperties and applyPatches are direct calls to the QIX Engine - Qlik Cloud's analytical core. Every wrong call generates an unnecessary re-layout, can overwrite another user's changes, or create bugs that only surface in production under real concurrent load.

Quick context: In the QIX Engine, every Qlik object (chart, filter, KPI) is a Generic Object with a properties schema. setProperties replaces that entire schema. applyPatches surgically modifies specific paths using JSON Patch (RFC 6902). Knowing when to use each is the difference between a resilient and a fragile mashup.
Mistake 01 of 05
BUG 01
Critical - Production
Race condition: not awaiting the Promise
The invisible bug that only shows up under real production load
Race Condition Stale Data Inconsistent UI

The most frequent and most deceptive mistake: calling setProperties without await, then immediately calling getLayout() expecting to see the updated properties. In a local dev environment it seems to work. In production with real network latency, the layout returns stale data.

Wrong - guaranteed race condition 
// setProperties is asynchronous
// no await = fire-and-forget
obj.setProperties(newProps);

// getLayout runs BEFORE set completes
const layout = await obj.getLayout();
// layout still has OLD data

// UI shows inconsistent state
updateChart(layout.qHyperCube);
Correct - guaranteed sequence 
// await ensures the QIX Engine
// processed before continuing
await obj.setProperties(newProps);

// now the layout reflects the new props
const layout = await obj.getLayout();
// layout has UPDATED data

// UI reflects correct state
updateChart(layout.qHyperCube);
⚠
Why it's critical: On connections with real latency (Qlik Cloud SaaS over the internet), the time between dispatching setProperties and receiving server confirmation can be 200-800ms. A getLayout without await frequently returns before that window, showing the user data from the previous state with no visible error.

Recommended pattern for chained updates

const updateAndRefresh = async (obj, changes) => {
  try {
    // 1. Get current state
    const current = await obj.getProperties();

    // 2. Apply changes, preserving the rest
    const updated = { ...current, ...changes };

    // 3. Wait for server confirmation
    await obj.setProperties(updated);

    // 4. Only then fetch the new layout
    return await obj.getLayout();
  } catch (err) {
    console.error('Failed to update object:', err);
    throw err;
  }
};
Mistake 02 of 05
BUG 02
Critical - Data Loss
Partial schema: overwriting without fetching current state
You silently delete measures, sorts and calculations
Data Loss Broken Chart Lost Sort

setProperties does a complete replace of the properties object in the QIX Engine. If you pass only part of the schema - for example, only the dimensions - everything not included in your object will be overwritten with defaults or deleted. This includes measures, sort configurations, color palettes, and tooltip customizations.

Wrong - deletes measures and sort 
// You want to change just the dimensions
await obj.setProperties({
  qHyperCubeDef: {
    qDimensions: newDimensions
    // qMeasures? DELETED
    // qSortCriteria? DELETED
    // qInitialDataFetch? DELETED
  }
  // showTitles? DELETED
  // title? DELETED
});
Correct - preserves everything 
// Always fetch current state first
const props = await obj.getProperties();

// Modify only what you need
props.qHyperCubeDef.qDimensions = newDimensions;

// Send back the complete object
await obj.setProperties(props);
// measures, sort, title: intact

Alternative: applyPatches for surgical changes

When you need to change only a specific field, applyPatches is safer and more efficient - no getProperties needed first:

// applyPatches uses JSON Patch (RFC 6902)
// No need for getProperties() first
await obj.applyPatches([
  {
    qOp: 'replace',
    qPath: '/qHyperCubeDef/qDimensions',
    qValue: JSON.stringify(newDimensions)
  }
]);

// To add to the end of an array:
await obj.applyPatches([
  {
    qOp: 'add',
    qPath: '/qHyperCubeDef/qDimensions/-',
    qValue: JSON.stringify(newDimension)
  }
]);
✅
Golden rule: Use applyPatches when you know the exact property path. Use setProperties + getProperties when the change is complex or involves multiple interdependent schema levels at once.
Mistake 03 of 05
BUG 03
High - Performance
Using setProperties where applyPatches would solve it
Every unnecessary call costs a full re-layout
Performance UI Latency

setProperties is a full replace operation: the QIX Engine receives the entire object, validates, persists, and fires an invalidation event that forces all dependent objects to recalculate. For changing a chart title, that's pure waste. applyPatches applies the patch server-side without re-serializing the full object.

Wrong - unnecessary overhead 
// Just to change the title...
const props = await obj.getProperties();
// 1 roundtrip + full object serialization

props.title = 'New Title';
await obj.setProperties(props);
// +1 roundtrip + full re-layout

// Total: 2 roundtrips to change 1 string
Correct - surgical patch 
// To change just the title:
await obj.applyPatches([{
  qOp: 'replace',
  qPath: '/title',
  qValue: JSON.stringify('New Title')
}]);
// 1 roundtrip, minimal patch
// no full object re-serialization
// Total: 1 roundtrip

Decision guide: which one to use?

Use applyPatches
  • + Change title or subtitle
  • + Add/remove a single dimension
  • + Toggle field visibility
  • + Update a measure expression
  • + Any known, exact path
Use setProperties
  • + Full hypercube reconstruction
  • + Multi-level changes together
  • + Switching visualization type
  • + Importing from a template config
  • + Complex, interdependent changes
Mistake 04 of 05
BUG 04
High - Critical Performance
Calls inside a loop without consolidating
N dimensions = N re-layouts. The server will notice
N Re-layouts Server Throttling Frozen UI

Every call to setProperties or applyPatches triggers a recalculation cycle in the QIX Engine. In loops that process arrays of dimensions or configurations, this multiplies the server workload by N. With 10 dimensions, you fire 10 sequential re-layouts when you could do 1.

Wrong - N calls in a loop 
// dimensions = ['Region', 'Customer', 'Product', ...]
for (const dim of dimensions) {
  const props = await obj.getProperties();
  props.qHyperCubeDef.qDimensions.push({
    qDef: { qFieldDefs: [dim] }
  });
  await obj.setProperties(props);
  // 1 getProperties + 1 setProperties per item
  // 10 dimensions = 20 roundtrips
}
Correct - one consolidated call 
// Fetch once, modify in memory
const props = await obj.getProperties();

// Process the entire array locally
const newDims = dimensions.map(dim => ({
  qDef: { qFieldDefs: [dim] }
}));

props.qHyperCubeDef.qDimensions = [
  ...props.qHyperCubeDef.qDimensions,
  ...newDims
];

// Single server call
await obj.setProperties(props);
// 10 dimensions = 2 roundtrips (1 get + 1 set)
⚡
Production throttling: Qlik Cloud applies per-session rate limiting. Loops with 50+ rapid calls can result in 429 Too Many Requests errors or server-imposed delays. Consolidating calls is the only effective solution.

When loops are unavoidable: batch with applyPatches

// applyPatches accepts an array of operations
// All applied in a single call to the server
const patches = dimensions.map((dim) => ({
  qOp: 'add',
  qPath: '/qHyperCubeDef/qDimensions/-',
  qValue: JSON.stringify({
    qDef: { qFieldDefs: [dim] }
  })
}));

// 1 call for N operations
await obj.applyPatches(patches);
Mistake 05 of 05
BUG 05
Medium - Resilience
No conflict handling between sessions
Two users edit the same object. Who wins? Neither
Silent Failure Overwritten Data Session Conflict

In mashups with multiple users or concurrent tabs, two processes can try to modify the same object nearly simultaneously. The QIX Engine rejects concurrent modifications with a specific error code (qError code 6 - conflict). Without handling this, the Promise is silently rejected and the user sees no error at all.

Wrong - invisible failure 
// No try/catch: error is swallowed
obj.setProperties(newProps);

// If another user was editing:
// - Promise rejected with code 6
// - No feedback to the user
// - Your changes silently lost
// - App continues as if it worked
Correct - with auto retry 
const setWithRetry = async (obj, getChanges, max = 3) => {
  for (let attempt = 0; attempt < max; attempt++) {
    try {
      const fresh = await obj.getProperties();
      const updated = getChanges(fresh);
      await obj.setProperties(updated);
      return; // success
    } catch (err) {
      if (err.qErrCode === 6 && attempt < max - 1) {
        // conflict: wait and retry
        await new Promise(r => setTimeout(r, 100));
        continue;
      }
      throw err;
    }
  }
};

Using the retry pattern

// Pass a function that knows how to apply the changes
await setWithRetry(obj, (currentProps) => {
  // currentProps always has the freshest state
  return {
    ...currentProps,
    title: 'Updated Dashboard',
    qHyperCubeDef: {
      ...currentProps.qHyperCubeDef,
      qDimensions: newDimensions
    }
  };
});

// If another user edited in between retries,
// the function receives updated props and re-applies
📚
About qErrCode 6: This code indicates the object was modified by another session since your last getProperties. The retry + re-fetch pattern ensures you always apply your changes on top of the latest state, preventing the race condition entirely.
