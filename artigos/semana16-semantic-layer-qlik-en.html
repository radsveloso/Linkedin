Semantic Layer in Qlik Cloud: The Missing Rail for AI Agents to Actually Work

Everyone is talking about AI Agents for data. Few are talking about what stops those agents from working well. The problem is almost always the same: the agent queried the wrong table, used the wrong field, and returned a number that does not exist.

The Problem That Kills the AI Agent Before It Starts

Imagine you connect an AI Agent to your data warehouse. The agent has access to all the tables. Someone asks: "What was the net revenue last month?"

The agent looks at the available tables and finds: fct_ord_v3, fct_ord_legacy, ord_all_regions_tmp. It doesn't know which one to use. It doesn't know if val_liquido or net_revenue_usd is the correct field. It doesn't know if the "net" logic already deducts returns or not.

Result: the agent guesses. And it probably gets it wrong.

Without semantic layer
-- What the agent sees:
fct_ord_v3
fct_ord_legacy
ord_all_regions_tmp

-- Available fields:
val_liquido
net_revenue_usd
receita_bruta
valor_final_v2

-- Agent decision: guesses.
Inaccurate or wrong answer
With semantic layer
-- What the agent sees:
MEASURE:  Net Revenue
Source:   fct_ord_v3.val_liquido
Filter:   status NOT IN ('cancelled')
Description:
  Revenue after returns.
  Excludes cancelled orders.

-- Agent decision: precise.
Reliable, governed answer

The difference is not in the AI Agent. It is in what the agent can see before answering. And that is exactly what the semantic layer solves.

What Is the Semantic Layer in the Qlik Context

In Qlik Cloud, the semantic layer is not a separate product. It is a set of configurations that you already have available and that transforms technical names into business context.

📐

Master Dimensions

Curated dimensions with a friendly name, description, and classification. When an agent searches for "Region", it finds the right dimension, not the raw field cd_reg_v2.

📊

Master Measures

Metrics with an expression, format, and description. "Net Revenue" is defined once and used in every chart and by every agent.

🔗

Business Logic

Configuration that defines how fields relate, which are measures vs. dimensions, and how to group fields into business concepts. It is the "vocabulary" Qlik Answers reads.

🤖

Logical Model

The model Qlik Answers indexes to answer natural-language questions. Only fields with correct classification and active visibility are included.

These four elements together form the Qlik Cloud semantic layer. Each is configurable. None requires additional infrastructure.

Architecture: dbt + Qlik + AI Agents

When you connect dbt to Qlik Cloud (as we covered in Week 15), the semantic layer sits between both sides: the transformed data arriving from the warehouse and the AI agents that will consume it.

Qlik Business Logic in Practice

Business Logic is configured via the UI in Qlik Cloud (app menu), but you can also export and version the configuration as JSON. Here is what each section controls:

business-logic-config.json (simplified structure)
// Field classification
{
  "fieldAttributes": [
    {
      "name": "val_liquido",
      "businessName": "Net Revenue",
      "description": "Revenue after returns and cancellations",
      "type": "measure",
      "visibility": "visible",
      "defaultAggregation": "Sum"
    },
    {
      "name": "nm_regiao",
      "businessName": "Region",
      "description": "Geographic region of the order",
      "type": "dimension",
      "visibility": "visible"
    },
    {
      "name": "cd_interno_produto",
      "visibility": "hidden"
      // internal fields stay hidden from agents
    }
  ],

  // Concept groups
  "conceptGroups": [
    {
      "name": "Financial",
      "fields": [
        "val_liquido",
        "val_bruto",
        "val_devolvido"
      ]
    }
  ]
}

What happens without this configuration

Qlik Answers indexes all fields in the app by default, including technical keys, internal flags, and temporary columns. The AI agent gets confused by names like flg_ativo_v2, dt_carga_etl, cd_hash_linha. Fields that make no sense for business questions should never reach the semantic model.

Most common mistake

Enabling Qlik Answers before configuring Business Logic. The agent will index everything, including technical fields it cannot interpret. The result is imprecise answers or questions Qlik Answers "cannot answer" even with the right data in the app. Configure Business Logic first. Always.

Master Items as the Contract Between BI and AI

Master Dimensions and Master Measures are the most visible layer of semantics in Qlik. When you create a Master Measure, you define the expression once and it becomes available for:

Dashboards built by any analyst, Qlik Answers when answering natural-language questions, and future integrations with external agents via API.

Creating a Master Measure via automation (JSON-RPC)
// Via Qlik Engine API
{
  "method": "CreateMeasure",
  "params": {
    "qProp": {
      "qInfo": {
        "qType": "measure"
      },
      "qMeasure": {
        "qLabel": "Net Revenue",
        "qDef": "Sum({<order_status-={'Cancelled','Returned'}>} val_liquido)",
        "qDescription": "Revenue excluding cancelled and returned orders"
      },
      "qMetaDef": {
        "tags": ["financial", "kpi"]
      }
    }
  }
}

When Qlik Answers receives the question "What was net revenue in October?", it looks in the Logical Model for the measure labeled "Net Revenue" and executes exactly that expression. It doesn't improvise. It doesn't recalculate differently. It uses what you defined.

dbt Semantic Layer as the Source of Truth Before Qlik

If you already use dbt (as we covered in Week 15), you can go one step further: define metrics in dbt with MetricFlow and use the warehouse as a bridge to Qlik. The advantage is that definitions live in one place, versioned in Git.

dbt/models/marts/schema.yml (metric definition)
semantic_models:
  - name: orders
    description: Semantic model for orders
    model: ref('mart_orders')
    defaults:
      agg_time_dimension: order_date

    entities:
      - name: order
        type: primary
        expr: order_id

    dimensions:
      - name: region
        type: categorical
        expr: nm_regiao
      - name: order_date
        type: time
        type_params:
          time_granularity: day

    measures:
      - name: net_revenue
        description: Revenue after cancellations and returns
        agg: sum
        expr: total_order_value
        create_metric: true

metrics:
  - name: net_revenue
    label: Net Revenue
    description: Primary revenue KPI
    type: simple
    type_params:
      measure: net_revenue
    filter: {{ Dimension('order__status') }} not in ('Cancelled', 'Returned')

Qlik Cloud consumes this definition via QVD exported from the warehouse. The load script (already lean after dbt) reads the result and populates the model. Qlik's Business Logic maps the net_revenue field to the correct business name.

The complete flow in three lines

Post-dbt load script (lean)
// Qlik Cloud load script after dbt did the heavy lifting

MART_ORDERS:
LOAD
    order_id            AS [Order ID],
    nm_regiao           AS [Region],
    order_date          AS [Order Date],
    net_revenue         AS [val_liquido]
FROM [lib://QVD/mart_orders.qvd]
(qvd);
// Business Logic and Master Measures do the rest.
// The agent queries "Net Revenue". It gets exactly that.

4 Pitfalls When Configuring the Semantic Layer for AI Agents

1

Leaving technical fields visible in the Logical Model

Fields like dt_carga_etl, sk_hash, flg_ativo have no meaning for business questions. If they stay visible, the agent will try them and fail. Rule: if a business analyst doesn't use the field in a dashboard, the field should be hidden in Business Logic.

2

Having the same metric with different names

"Revenue", "Sales", and "Net Revenue" in the same app create ambiguity for the agent. It doesn't know which to use and may mix them. Define a single canonical name for each metric and use Business Logic synonyms to map variations.

3

Not classifying fields as measure or dimension

Without classification, Qlik Answers must infer by data type. Inference is error-prone: numeric ID fields can become measures, dates can become incorrect dimensions. Explicit classification is the difference between an agent that understands the model and one that guesses.

4

Ignoring the Logical Model Group

Master Items with correct visibility are not automatically indexed if they are not in a Logical Model Group. This is the most silent error: Business Logic appears configured, but Qlik Answers responds as if the data doesn't exist. Verify that the group is active and includes the right items.

What Changes in Practice

In a real app with more than 80 fields, configuring the semantic layer before enabling Qlik Answers produced measurable results:

87%
questions answered accurately by Qlik Answers
23
visible fields (out of 80+ technical fields in the model)
0
metric ambiguities reported by users

The aggressive filter (23 fields out of 80+) was the most important decision. Fewer options for the agent means less chance of wrong choices. A good semantic layer is a lean semantic layer.

Checklist: Semantic Layer Ready for AI Agents

✓
All technical fields (keys, flags, hashes) are marked as hidden in Business Logic
✓
Each measure has a businessName and description in business language
✓
Dimensions and measures are explicitly classified (not inferred)
✓
Logical Model Group created and active, containing the correct Master Items
✓
No duplicate metric names in the same app
✓
Synonyms configured for alternative business terms
✓
Tested with at least 10 real questions before opening to users

The Semantic Layer Is the Foundation. Not the Finish Line.

Before enabling any AI Agent on your data, ask: what is it going to see? If the answer is "the raw warehouse tables", the agent will fail. If the answer is "a governed semantic layer", the agent will succeed.

Qlik Answers, Copilot, external agents via API: all depend on the same principle. Data without context is not knowledge. It is noise.
