O problema que ninguém fala abertamente

Toda empresa que usa Qlik há alguns anos tem alguma versão deste cenário: um load script de centenas (às vezes milhares) de linhas, cheio de transformações que só uma ou duas pessoas entendem. Nao tem documentação. Os campos têm nomes que faziam sentido em 2019. Se você perguntar "de onde vem esse campo?", a resposta honesta é "precisa rastrear no script".

Isso não é culpa do Qlik. É a consequência natural de transformações de dados vivendo dentro de uma ferramenta de visualização, sem o rigor de engenharia de software aplicado.

Analytics Engineering é a disciplina que surgiu para resolver isso: aplicar práticas de engenharia de software (versionamento, testes, documentação, modularidade) ao trabalho de transformação de dados. O dbt é a ferramenta central dessa disciplina.

O ponto central: dbt faz o T do ELT no warehouse. O load script do Qlik deixa de ser o lugar onde você transforma dados brutos em dados limpos. Ele passa a ser mais enxuto, responsável por carregar dados já tratados para QVDs otimizados.

Antes e depois: comparação de código real

Transformação típica no load script Qlik

Um exemplo real de como transformações ficam misturadas com a carga no script:

ANTES: Load script Qlik com transformação embutida
// orders.qvs: transformacao + carga misturadas
// Quem criou isso? Quando? Por que esse filtro existe?

Orders_Temp:
LOAD
    num(num_ped) AS OrderID,
    date(makedate(
        left(dt_ped,4),
        mid(dt_ped,5,2),
        right(dt_ped,2)
    ), 'YYYY-MM-DD') AS OrderDate,
    if(cd_sit_ped = 'A', 'Ativo',
       if(cd_sit_ped = 'F', 'Faturado',
          if(cd_sit_ped = 'C', 'Cancelado', 'Desconhecido')
       )
    ) AS OrderStatus,
    vl_tot_ped * 1 AS TotalOrderValue,
    cd_cliente AS CustomerID
FROM [lib://DataConnection/orders.csv]
WHERE cd_sit_ped <> 'X'  // filtro legado: nao remover (ninguem sabe por que)
AND  year(makedate(left(dt_ped,4),mid(dt_ped,5,2),right(dt_ped,2))) >= 2020;

// 40 linhas mais pra baixo, um JOIN que depende da tabela acima
// e ninguem testou se OrderID é realmente unico...
DEPOIS: dbt model, transformacao no warehouse, testada e documentada
-- models/staging/stg_orders.sql
-- Responsavel: time de dados | Atualizado: 2026-10

WITH source AS (
    SELECT * FROM {{ source('erp_raw', 'orders') }}
),

renamed AS (
    SELECT
        CAST(num_ped AS INTEGER)          AS order_id,
        TO_DATE(dt_ped, 'YYYYMMDD')         AS order_date,
        cd_sit_ped                         AS status_code,
        vl_tot_ped                         AS total_order_value,
        cd_cliente                         AS customer_id

    FROM source
    -- filtro legado documentado com motivo
    WHERE cd_sit_ped != 'X'  -- exclui registros de teste (cd X = ambiente dev)
    AND   dt_ped >= '20200101'

),

mapped_status AS (
    SELECT
        * EXCLUDE (status_code),
        CASE status_code
            WHEN 'A' THEN 'Ativo'
            WHEN 'F' THEN 'Faturado'
            WHEN 'C' THEN 'Cancelado'
            ELSE 'Desconhecido'
        END AS order_status
    FROM renamed
)

SELECT * FROM mapped_status

O schema.yml: documentação que nao fica pra trás

# models/staging/schema.yml
version: 2

models:
  - name: stg_orders
    description: "Pedidos do ERP normalizados e filtrados. Exclui registros de ambiente de desenvolvimento (status X) e pedidos anteriores a 2020."

    columns:
      - name: order_id
        description: "Identificador unico do pedido (origem: num_ped)"
        tests:
          - not_null
          - unique

      - name: order_date
        description: "Data do pedido convertida de YYYYMMDD para DATE"
        tests:
          - not_null

      - name: order_status
        description: "Status legivel do pedido mapeado de codigos internos do ERP"
        tests:
          - accepted_values:
              values: ['Ativo', 'Faturado', 'Cancelado', 'Desconhecido']

      - name: total_order_value
        description: "Valor total do pedido em moeda local"
        tests:
          - not_null

O que acontece quando você roda dbt test: todos os testes acima executam contra o warehouse antes de qualquer dado chegar ao Qlik. Se order_id nao for unico, o pipeline para. Nao existe equivalente nativo disso num load script tradicional.

Os 4 superpoderes do dbt para times Qlik

✅ Testes automáticos de qualidade

not_null, unique, accepted_values, relationships entre tabelas. Rodando antes do dado chegar ao Qlik Cloud. Adeus script de QA manual.

📄 Documentação gerada

dbt docs generate cria um site com lineage visual, descrições de campos e testes. Atualiza a cada execução. Sem Excel de metadados desatualizado.

🌟 Lineage de ponta a ponta

Você sabe exatamente quais modelos dependem de qual fonte. Quando uma tabela muda no ERP, você ve o impacto antes de executar qualquer coisa.

🏠 Git como base

Pull requests, code review, branches para desenvolvimento. Dois analistas podem trabalhar em modelos diferentes em paralelo sem sobrescrever o trabalho um do outro.

Como o load script Qlik fica depois do dbt

O load script nao desaparece. Ele fica mais enxuto e com responsabilidade mais clara: carregar dados ja tratados do warehouse para QVDs otimizados para o motor associativo do Qlik.

load script Qlik pós-dbt: enxuto e de responsabilidade clara
// orders.qvs (pos-dbt)
// Dados ja tratados no warehouse pelo dbt. Aqui so carga + QVD.

LIB CONNECT TO 'Snowflake_Connection';

Orders:
LOAD
    order_id       AS %OrderID,
    order_date     AS OrderDate,
    order_status   AS OrderStatus,
    total_order_value AS TotalOrderValue,
    customer_id    AS %CustomerID
FROM (snowflake, query is
    "SELECT * FROM analytics.mart_orders WHERE order_date >= dateadd(year,-2,current_date)"
);

STORE Orders INTO [lib://QVD/Orders.qvd] (qvd);
DROP TABLE Orders;

Resultado: o load script vira um orquestrador de carga, nao um motor de transformação. Isso significa scripts menores, mais faceis de manter e sem aquelas transformações aninhadas que ninguem ousa tocar.

Integração prática: dbt + QVD Layer + Qlik Cloud

O ponto de integração mais eficiente é a camada de marts no dbt alimentando diretamente a geração de QVDs. Um padrão que funciona bem na pratica:

models/marts/mart_orders.sql: modelo final pronto para o Qlik
-- Mart final: dados prontos para consumo pelo Qlik Cloud
-- Granularidade: pedido. Nao agrega aqui; o Qlik faz isso melhor.

WITH orders AS (
    SELECT * FROM {{ ref('stg_orders') }}
),

customers AS (
    SELECT * FROM {{ ref('stg_customers') }}
),

products AS (
    SELECT * FROM {{ ref('stg_order_items') }}
)

SELECT
    o.order_id,
    o.order_date,
    o.order_status,
    o.total_order_value,
    o.customer_id,
    c.customer_name,
    c.customer_segment,
    c.customer_region

FROM orders    o
JOIN customers c USING (customer_id)

-- Sem GROUP BY aqui: o motor associativo do Qlik agrega melhor
-- que qualquer pre-agregacao feita no SQL

Erro comum: tentar pre-agregar no dbt para "ajudar" o Qlik. O motor associativo do Qlik e muito mais eficiente fazendo agregações dinamicas do que receber dados pre-agregados. O dbt entrega granularidade maxima; o Qlik agrega na hora da visualização.

Armadilhas de quem adota dbt sem planejamento

  • 1
    Replicar o load script inteiro no dbt Migrar transformações uma a uma sem repensar a arquitetura nao traz os beneficios. Aproveite para redesenhar as camadas: staging (dados brutos limpos), intermediate (logica de negocio) e marts (prontos para o Qlik).
  • 2
    Fazer dbt gerar QVDs diretamente dbt é SQL no warehouse. QVDs sao o formato binario do Qlik. Eles nao se misturam. O fluxo correto: dbt cria tabelas no warehouse, o load script Qlik le essas tabelas e gera QVDs.
  • 3
    Adotar dbt sem Git configurado dbt sem controle de versao real e so mais complexidade. O valor da ferramenta vem da combinacao: SQL versionado + testes + documentação. Sem Git, voce tem metade de uma solucao.
  • 4
    Esperar que o dbt resolva problemas de governança Se os dados na fonte estao ruins, o dbt vai apenas revelar isso com mais clareza. Ele nao limpa dados magicamente: ele testa e documenta. A qualidade na fonte continua sendo responsabilidade do time.
  • 5
    Ignorar a orquestração dbt roda models. Quem agenda? Quem garante que o dbt termina antes do reload Qlik começar? Voce precisa de um orquestrador (Airflow, Prefect, dbt Cloud Scheduler, ou ate o proprio Qlik Cloud Reload Tasks com dependências).

Caso de referência: distribuidora industrial

Checklists de implementação

Para o Gestor

  • Avaliar se o time tem proficiencia em SQL e Git antes de iniciar
  • Definir qual warehouse sera o ponto central (Snowflake, BigQuery, Redshift)
  • Decidir entre dbt Core (open source) e dbt Cloud (gerenciado)
  • Planejar migracao incremental: novos projetos em dbt, legado migra gradualmente
  • Garantir que orquestração de pipelines esta definida antes do go-live

Para o Desenvolvedor

  • Estruturar camadas: staging / intermediate / marts antes de escrever SQL
  • Escrever schema.yml simultaneamente ao model, nunca depois
  • Definir testes minimos para toda chave primaria: not_null + unique
  • Manter load script Qlik apenas para carga + QVD, transformações saem dele
  • Configurar dependência de reload: dbt termina antes do Qlik recarregar
  • Usar dbt docs serve para validar lineage antes de apresentar para o gestor
