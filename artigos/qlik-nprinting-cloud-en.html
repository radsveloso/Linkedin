The ignored reality

Why the migration is not straightforward

Qlik Cloud was built for interactive SaaS analytics. NPrinting was built for pixel-precise, scaled report distribution. They are fundamentally different products with different design philosophies. Moving from one to the other is not an upgrade - it is a transformation.

🏗️
NPrinting still runs on Windows Server
To this day, the NPrinting Server requires on-premises or IaaS Windows infrastructure. There is no cloud-native version. It connects to Qlik Sense Enterprise (Windows) or QlikView - not directly to Qlik Cloud.
📊
Qlik Cloud Reporting still has gaps
Qlik Cloud's native Reporting has improved significantly, but it still lacks Word, PowerPoint, and pixel-perfect Excel template support - all mandatory in regulated, financial, and pharmaceutical environments.
🔀
Burst reporting is the real bottleneck
Generating 500 reports with different filters per recipient, on a schedule, automatically - this is the use case where Qlik Cloud has not yet reached NPrinting's maturity. No available workaround is elegant.
⚠️
Vendors downplay the complexity
In cloud migration sales cycles, the focus stays on SaaS benefits. Reporting gaps rarely appear in the vendor's deck. They show up at go-live, when critical reports stop working and stakeholders are watching.
Exclusive capabilities

What NPrinting does that Cloud Reporting still does not

Before committing to any migration timeline, map which NPrinting capabilities are actually in use in your environment. These are the ones that most consistently stall production migrations.

📄
Pixel-perfect templates
Map specific Excel cells, Word tables, and PowerPoint slides with millimeter precision. Regulatory submissions require this - any layout deviation can trigger rejection.
📨
Granular burst reporting
One template, N recipients, each receiving their own filtered dataset. With scheduling, execution conditions, and per-recipient delivery logs built in - no custom code required.
🗞️
NewsStand portal
A self-service portal where consumers access on-demand reports without needing a Qlik Sense license. Common in enterprises with large populations of read-only report consumers.
🗂️
Multi-format output
Excel (.xlsx), Word (.docx), PowerPoint (.pptx), PDF, HTML, and CSV from the same scheduled task. Cloud Reporting currently focuses primarily on PDF and basic table exports.
⏰
Dependency-aware scheduling
Native pipeline logic: "run this report only after this app's reload completes successfully." Task chaining with retry logic and failure notification baked in - no third-party orchestration needed.
👥
AD/LDAP integration
Report distribution based on Active Directory groups. When a user joins or leaves a group, they automatically start or stop receiving reports - no manual recipient list maintenance required.
Real architecture

How NPrinting connects to Qlik Cloud

NPrinting does not connect directly to Qlik Cloud to generate reports. The actual flow is counterintuitive, and most teams discover this too late in the project - usually the week before go-live.

      |

      |  // NPrinting READS data from Cloud apps
      |  // but the SERVER still runs on-prem
      v

  |  processes templates with Cloud app data
      v

// ===================================================
// SCENARIO C: Cloud-native only (current gap)
// ===================================================

Qlik Cloud Reporting (native, serverless)
  |  PDF of apps and stories
  |  tables in CSV / basic Excel (no formatting)
  |  simple email scheduling
      v
Works well for simple use cases
// DOES NOT replace NPrinting for complex reports
Critical point for your project
The Qlik NPrinting Connector for Qlik Cloud lets NPrinting read data from cloud apps to generate reports. But NPrinting itself still runs on Windows infrastructure. Do not confuse "connected to the cloud" with "running in the cloud" - they are fundamentally different things that have very different implications for your architecture and maintenance overhead.

What most people miss

The hybrid state will last years

After working through dozens of Qlik Cloud migration projects, the pattern is consistent. Accepting this reality earlier saves significant time, budget, and political capital.

The reality the kickoff deck hides
Enterprises with regulatory reporting obligations - financial services, pharma, manufacturing - cannot migrate NPrinting in six months. The hybrid architecture (Qlik Cloud for analytics plus NPrinting for formatted reporting) is not a temporary workaround. For most large organizations, it is the realistic 3 to 5 year strategy. Plan accordingly.
🎯
Inventory before you migrate
Catalog every active NPrinting report: template, output format, recipients, frequency, owner, and last confirmed usage date. Most teams discover that 30% of reports are no longer consumed by anyone - instant scope reduction.
🔄
Start with the simple ones
PDFs and basic CSV tables migrate to Qlik Cloud Reporting today with no blockers. This reduces NPrinting load and builds migration muscle memory before you tackle the high-stakes reports.
📡
Track the Qlik roadmap
Qlik is actively investing in Cloud Reporting. What is missing today may ship in 6 to 12 months. Rewriting complex templates before feature parity arrives is guaranteed rework - a very common and very avoidable mistake.
📋
Document hidden dependencies
Many organizations do not know how many NPrinting reports exist or which are business-critical. A full audit before migration is mandatory. Find the "orphan reports" that nobody remembers but that someone uses every month-end close.
Practical roadmap

6 steps to migrate without chaos

This is the flow that actually works in practice - not what appears in the vendor's slide deck. Adapt it to your context, but do not skip the inventory and classification phases. They save the project.

1
Run a full inventory
List every NPrinting report: template, output format, recipients, schedule, technical owner, and last confirmed usage date. Most teams discover 30% of reports have no active consumers - instant scope reduction with zero migration risk.
Tool: NPrinting REST API or manual export from the NPrinting Console
2
Classify by complexity and business criticality
Simple: app PDF, basic CSV. Medium: tabular Excel without advanced formatting. Complex: pixel-perfect Excel, fixed-layout Word, corporate PowerPoint. Critical: regulatory or financial reports with SLA requirements and audit trails.
Deliverable: prioritization matrix with effort vs. criticality scoring
3
Migrate the simple ones first via Qlik Cloud Reporting
PDFs and basic tables migrate today with no technical blockers. This reduces NPrinting load and builds the team's migration process before you tackle high-stakes reports. Target: decommission 40% of NPrinting reports within the first 60 days.
Quick win: validate the migration pipeline with low-risk, high-volume reports
4
Configure the NPrinting Connector for Qlik Cloud
For complex reports that stay in NPrinting, configure the connector so it reads data from Qlik Cloud apps. This lets you maintain NPrinting's reporting capabilities while your analytics apps fully migrate to the cloud - without rewriting your most critical templates now.
Reference: Qlik Help - "NPrinting Connector for Qlik Cloud"
5
Monitor the roadmap before rewriting complex templates
Before investing engineering effort in rewriting pixel-perfect Excel templates to an alternative format, verify whether Qlik Cloud Reporting will deliver the capability in the next 6 to 12 months. Premature rewrites are the single largest source of wasted effort in these projects.
Resource: Qlik Ideation portal + quarterly Qlik Cloud release notes
6
Define clear decommissioning criteria upfront
Document the technical conditions for shutting down NPrinting: "when Qlik Cloud Reporting supports pixel-perfect Excel templates AND granular burst reporting with per-recipient filters." With explicit criteria, the decommissioning decision becomes a technical milestone - not a political negotiation.
Deliverable: documented Go/No-Go criteria for NPrinting decommissioning
