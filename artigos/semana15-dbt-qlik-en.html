The problem no one talks about openly

Every company that has been using Qlik for a few years has some version of this scenario: a load script with hundreds (sometimes thousands) of lines, full of transformations that only one or two people understand. No documentation. Fields with names that made sense in 2019. If you ask "where does this field come from?", the honest answer is "you need to trace it through the script."

This is not Qlik's fault. It is the natural consequence of data transformations living inside a visualization tool, without software engineering rigor applied to them.

Analytics Engineering is the discipline that emerged to solve this: applying software engineering practices (versioning, testing, documentation, modularity) to data transformation work. dbt is the central tool of this discipline.

The key point: dbt handles the T in ELT inside the warehouse. The Qlik load script stops being the place where you transform raw data into clean data. It becomes leaner, responsible for loading already-processed data into optimized QVDs.

Before and after: real code comparison

Typical transformation in the Qlik load script

A real example of how transformations get mixed with data loading in the script:

BEFORE: Qlik load script with embedded transformation
// orders.qvs: transformation + load mixed together
// Who created this? When? Why does this filter exist?

Orders_Temp:
LOAD
    num(num_ped) AS OrderID,
    date(makedate(
        left(dt_ped,4),
        mid(dt_ped,5,2),
        right(dt_ped,2)
    ), 'YYYY-MM-DD') AS OrderDate,
    if(cd_sit_ped = 'A', 'Active',
       if(cd_sit_ped = 'F', 'Invoiced',
          if(cd_sit_ped = 'C', 'Cancelled', 'Unknown')
       )
    ) AS OrderStatus,
    vl_tot_ped * 1 AS TotalOrderValue,
    cd_cliente AS CustomerID
FROM [lib://DataConnection/orders.csv]
WHERE cd_sit_ped <> 'X'  // legacy filter, do not remove (nobody knows why)
AND  year(makedate(left(dt_ped,4),mid(dt_ped,5,2),right(dt_ped,2))) >= 2020;

// 40 lines below, a JOIN that depends on the table above
// and nobody tested whether OrderID is actually unique...
AFTER: dbt model, transformation in the warehouse, tested and documented
-- models/staging/stg_orders.sql
-- Owner: data team | Last updated: 2026-10

WITH source AS (
    SELECT * FROM {{ source('erp_raw', 'orders') }}
),

renamed AS (
    SELECT
        CAST(num_ped AS INTEGER)          AS order_id,
        TO_DATE(dt_ped, 'YYYYMMDD')         AS order_date,
        cd_sit_ped                         AS status_code,
        vl_tot_ped                         AS total_order_value,
        cd_cliente                         AS customer_id

    FROM source
    -- legacy filter documented with reason
    WHERE cd_sit_ped != 'X'  -- excludes test records (code X = dev environment)
    AND   dt_ped >= '20200101'

),

mapped_status AS (
    SELECT
        * EXCLUDE (status_code),
        CASE status_code
            WHEN 'A' THEN 'Active'
            WHEN 'F' THEN 'Invoiced'
            WHEN 'C' THEN 'Cancelled'
            ELSE 'Unknown'
        END AS order_status
    FROM renamed
)

SELECT * FROM mapped_status

The schema.yml: documentation that stays current

# models/staging/schema.yml
version: 2

models:
  - name: stg_orders
    description: "ERP orders normalized and filtered. Excludes development environment records (status X) and orders prior to 2020."

    columns:
      - name: order_id
        description: "Unique order identifier (source: num_ped)"
        tests:
          - not_null
          - unique

      - name: order_date
        description: "Order date converted from YYYYMMDD to DATE"
        tests:
          - not_null

      - name: order_status
        description: "Human-readable order status mapped from internal ERP codes"
        tests:
          - accepted_values:
              values: ['Active', 'Invoiced', 'Cancelled', 'Unknown']

      - name: total_order_value
        description: "Total order value in local currency"
        tests:
          - not_null

What happens when you run dbt test: every test above executes against the warehouse before any data reaches Qlik. If order_id is not unique, the pipeline stops. There is no native equivalent of this in a traditional load script.

The 4 superpowers of dbt for Qlik teams

✅ Automated quality tests

not_null, unique, accepted_values, relationships between tables. Running before data reaches Qlik Cloud. Goodbye manual QA scripts.

📄 Generated documentation

dbt docs generate creates a site with visual lineage, field descriptions, and tests. Updates with every run. No more stale metadata spreadsheets.

🌟 End-to-end lineage

You know exactly which models depend on which source. When a table changes in the ERP, you see the impact before running anything.

🏠 Git as a foundation

Pull requests, code review, feature branches. Two analysts can work on different models in parallel without overwriting each other's work.

What the Qlik load script looks like after dbt

The load script does not disappear. It becomes leaner with a clearer responsibility: loading already-processed data from the warehouse into QVDs optimized for Qlik's associative engine.

Qlik load script post-dbt: lean and with clear responsibility
// orders.qvs (post-dbt)
// Data already processed in the warehouse by dbt. Only load + QVD here.

LIB CONNECT TO 'Snowflake_Connection';

Orders:
LOAD
    order_id       AS %OrderID,
    order_date     AS OrderDate,
    order_status   AS OrderStatus,
    total_order_value AS TotalOrderValue,
    customer_id    AS %CustomerID
FROM (snowflake, query is
    "SELECT * FROM analytics.mart_orders WHERE order_date >= dateadd(year,-2,current_date)"
);

STORE Orders INTO [lib://QVD/Orders.qvd] (qvd);
DROP TABLE Orders;

Result: the load script becomes a load orchestrator, not a transformation engine. This means smaller scripts, easier to maintain, and without those nested transformations nobody dares to touch.

Practical integration: dbt + QVD Layer + Qlik Cloud

The most efficient integration point is the dbt marts layer feeding directly into QVD generation. A pattern that works well in practice:

models/marts/mart_orders.sql: final model ready for Qlik
-- Final mart: data ready for Qlik Cloud consumption
-- Granularity: order. No aggregation here; Qlik does that better.

WITH orders AS (
    SELECT * FROM {{ ref('stg_orders') }}
),

customers AS (
    SELECT * FROM {{ ref('stg_customers') }}
),

products AS (
    SELECT * FROM {{ ref('stg_order_items') }}
)

SELECT
    o.order_id,
    o.order_date,
    o.order_status,
    o.total_order_value,
    o.customer_id,
    c.customer_name,
    c.customer_segment,
    c.customer_region

FROM orders    o
JOIN customers c USING (customer_id)

-- No GROUP BY here: Qlik's associative engine aggregates
-- much better than any pre-aggregation done in SQL

Common mistake: trying to pre-aggregate in dbt to "help" Qlik. Qlik's associative engine is much more efficient doing dynamic aggregations than receiving pre-aggregated data. dbt delivers maximum granularity; Qlik aggregates at visualization time.

Pitfalls when adopting dbt without planning

  • 1
    Replicating the entire load script in dbt Migrating transformations one by one without rethinking the architecture brings no real benefit. Use the migration to redesign the layers: staging (clean raw data), intermediate (business logic), and marts (ready for Qlik).
  • 2
    Trying to make dbt generate QVDs directly dbt is SQL in the warehouse. QVDs are Qlik's binary format. They do not mix. The correct flow: dbt creates tables in the warehouse, the Qlik load script reads those tables and generates QVDs.
  • 3
    Adopting dbt without Git configured dbt without real version control is just more complexity. The tool's value comes from the combination: versioned SQL + tests + documentation. Without Git, you have half a solution.
  • 4
    Expecting dbt to solve governance problems If the data at the source is bad, dbt will only reveal that more clearly. It does not magically clean data: it tests and documents. Source quality remains the team's responsibility.
  • 5
    Ignoring orchestration dbt runs models. Who schedules them? Who ensures dbt finishes before the Qlik reload starts? You need an orchestrator: Airflow, Prefect, dbt Cloud Scheduler, or even Qlik Cloud Reload Tasks with dependencies configured.

Implementation checklists

For the Manager

  • Assess whether the team is proficient in SQL and Git before starting
  • Define which warehouse will be the central point (Snowflake, BigQuery, Redshift)
  • Decide between dbt Core (open source) and dbt Cloud (managed)
  • Plan incremental migration: new projects in dbt, legacy migrates gradually
  • Ensure pipeline orchestration is defined before go-live

For the Developer

  • Structure layers: staging / intermediate / marts before writing SQL
  • Write schema.yml alongside the model, never after
  • Define minimum tests for every primary key: not_null + unique
  • Keep Qlik load script for load + QVD only, transformations move out
  • Configure reload dependency: dbt finishes before Qlik reloads
  • Use dbt docs serve to validate lineage before presenting to management
