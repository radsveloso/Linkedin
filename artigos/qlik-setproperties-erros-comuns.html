Por que isso importa

A API que todo dev usa, mas poucos dominam

setProperties e applyPatches sao chamadas diretas ao QIX Engine, o motor analitico do Qlik Cloud. Cada chamada errada gera um re-layout desnecessario, pode sobrescrever dados de outro usuario ou criar bugs que so aparecem em producao com multiplas sessoes concorrentes.

Contexto rapido: No QIX Engine, cada objeto do Qlik (grafico, filtro, KPI) e representado como um Generic Object com um esquema de propriedades. setProperties substitui esse esquema inteiro. applyPatches modifica cirurgicamente paths especificos usando JSON Patch (RFC 6902).
Erro 01 de 05
ERRO 01
Critico - Producao
Race condition: nao aguardar a Promise
O bug invisivel que so aparece sob carga real
Race Condition Dados desatualizados UX inconsistente

Este e o erro mais frequente e o mais traicoeiro: chamar setProperties sem await, e em seguida fazer um getLayout() esperando ver as propriedades atualizadas. Em ambiente de desenvolvimento com conexao local, parece funcionar. Em producao, com latencia real, o layout retorna dados antigos.

Errado - race condition garantida 
// setProperties e assíncrono
// sem await = fire-and-forget
obj.setProperties(newProps);

// getLayout executa ANTES do set completar
const layout = await obj.getLayout();
// layout ainda tem os dados ANTIGOS

// UI mostra estado inconsistente
updateChart(layout.qHyperCube);
Correto - sequencia garantida 
// await garante que o QIX Engine
// processou antes de continuar
await obj.setProperties(newProps);

// agora o layout reflete as novas props
const layout = await obj.getLayout();
// layout tem os dados ATUALIZADOS

// UI reflete o estado correto
updateChart(layout.qHyperCube);
⚠
Por que e critico: Em conexoes com latencia alta (Qlik Cloud SaaS via internet), o tempo entre o disparo de setProperties e a confirmacao do servidor pode ser de 200-800ms. O getLayout sem await frequentemente retorna antes desse intervalo, mostrando ao usuario dados do estado anterior sem nenhum erro visivel.

Padrao recomendado para atualizacoes em cadeia

const updateAndRefresh = async (obj, changes) => {
  try {
    // 1. Busca estado atual
    const current = await obj.getProperties();

    // 2. Aplica mudancas preservando o resto
    const updated = { ...current, ...changes };

    // 3. Aguarda confirmacao do servidor
    await obj.setProperties(updated);

    // 4. So entao busca o novo layout
    return await obj.getLayout();
  } catch (err) {
    console.error('Falha ao atualizar objeto:', err);
    throw err;
  }
};
Erro 02 de 05
ERRO 02
Critico - Perda de Dados
Schema parcial: sobrescrever sem buscar o estado atual
Voce apaga medidas, sorts e calculos sem perceber
Perda de Dados Grafico quebrado Sort perdido

setProperties faz um replace completo do objeto de propriedades no QIX Engine. Se voce passar apenas uma parte do schema - por exemplo, so as dimensoes - tudo o que nao estiver no seu objeto enviado sera sobrescrito com valores default ou apagado. Isso inclui medidas, configuracoes de sort, paletas de cores e customizacoes de tooltip.

Errado - apaga medidas e sort 
// Voce quer mudar so as dimensoes
await obj.setProperties({
  qHyperCubeDef: {
    qDimensions: newDimensions
    // qMeasures? APAGADAS
    // qSortCriteria? APAGADO
    // qInitialDataFetch? APAGADO
  }
  // showTitles? APAGADO
  // title? APAGADO
});
Correto - preserva tudo 
// Sempre busca o estado atual primeiro
const props = await obj.getProperties();

// Modifica apenas o que precisa
props.qHyperCubeDef.qDimensions = newDimensions;

// Envia o objeto completo de volta
await obj.setProperties(props);
// medidas, sort, titulo: intactos

Alternativa: applyPatches para mudancas cirurgicas

Quando voce precisa mudar apenas um campo especifico, applyPatches e mais seguro e mais eficiente - nao precisa buscar as propriedades antes:

// applyPatches usa JSON Patch (RFC 6902)
// Nao requer getProperties() antes
await obj.applyPatches([
  {
    qOp: 'replace',
    qPath: '/qHyperCubeDef/qDimensions',
    qValue: JSON.stringify(newDimensions)
  }
]);

// Para adicionar ao final de um array:
await obj.applyPatches([
  {
    qOp: 'add',
    qPath: '/qHyperCubeDef/qDimensions/-',
    qValue: JSON.stringify(newDimension)
  }
]);
✅
Regra de ouro: Use applyPatches quando voce sabe o path exato da propriedade. Use setProperties + getProperties quando a mudanca e complexa ou envolve multiplos niveis de schema simultaneamente.
Erro 03 de 05
ERRO 03
Alto - Performance
Usar setProperties onde applyPatches resolve
Cada chamada desnecessaria custa um re-layout completo
Performance Latencia de UI

setProperties e uma operacao de full replace: o QIX Engine recebe o objeto inteiro, valida, persiste e dispara um evento de invalidacao que forca todos os objetos dependentes a recalcular. Para mudar o titulo de um grafico, isso e desperdicio. applyPatches faz o patch no servidor sem re-serializar o objeto inteiro.

Errado - overhead desnecessario 
// Para mudar so o titulo...
const props = await obj.getProperties();
// 1 roundtrip + serializacao do objeto inteiro

props.title = 'Novo Titulo';
await obj.setProperties(props);
// +1 roundtrip + re-layout completo

// Total: 2 roundtrips para mudar 1 string
Correto - patch cirurgico 
// Para mudar so o titulo:
await obj.applyPatches([{
  qOp: 'replace',
  qPath: '/title',
  qValue: JSON.stringify('Novo Titulo')
}]);
// 1 roundtrip, patch minimo
// sem re-serializar o objeto inteiro
// Total: 1 roundtrip

Guia de decisao: qual usar?

Use applyPatches
  • + Mudar titulo, subtitulo
  • + Adicionar/remover 1 dimensao
  • + Mudar visibilidade de campo
  • + Atualizar expressao de medida
  • + Qualquer path exato e conhecido
Use setProperties
  • + Reconstrucao completa do hipercubo
  • + Mudancas em multiplos niveis
  • + Trocar tipo de visualizacao
  • + Importar config de template
  • + Mudancas complexas e interdependentes
Erro 04 de 05
ERRO 04
Alto - Performance Critica
Chamadas em loop sem consolidar
N dimensoes = N re-layouts. O servidor agradece nao fazer isso
N re-layouts Throttling do servidor UI trava em loop

Cada chamada a setProperties ou applyPatches dispara um ciclo de recalculo no QIX Engine. Em loops que processam arrays de dimensoes ou configuracoes, isso multiplica o trabalho do servidor por N. Com 10 dimensoes, voce dispara 10 re-layouts em sequencia quando poderia fazer 1.

Errado - N chamadas em loop 
// dimensoes = ['Regiao', 'Cliente', 'Produto', ...]
for (const dim of dimensoes) {
  const props = await obj.getProperties();
  props.qHyperCubeDef.qDimensions.push({
    qDef: { qFieldDefs: [dim] }
  });
  await obj.setProperties(props);
  // 1 getProperties + 1 setProperties por item
  // 10 dimensoes = 20 roundtrips
}
Correto - uma chamada consolidada 
// Busca uma vez, modifica em memoria
const props = await obj.getProperties();

// Processa todo o array localmente
const newDims = dimensoes.map(dim => ({
  qDef: { qFieldDefs: [dim] }
}));

props.qHyperCubeDef.qDimensions = [
  ...props.qHyperCubeDef.qDimensions,
  ...newDims
];

// Uma unica chamada ao servidor
await obj.setProperties(props);
// 10 dimensoes = 2 roundtrips (1 get + 1 set)
⚡
Throttling em producao: O Qlik Cloud aplica rate limiting por sessao. Loops de 50+ chamadas rapidas podem resultar em erros 429 Too Many Requests ou atrasos impostos pelo servidor. Consolidar as chamadas e a unica solucao efetiva.

Quando loops sao inevitaveis: use applyPatches em batch

// applyPatches aceita um array de operacoes
// Todas aplicadas em uma unica chamada
const patches = dimensoes.map((dim, i) => ({
  qOp: 'add',
  qPath: '/qHyperCubeDef/qDimensions/-',
  qValue: JSON.stringify({
    qDef: { qFieldDefs: [dim] }
  })
}));

// 1 chamada para N operacoes
await obj.applyPatches(patches);
Erro 05 de 05
ERRO 05
Medio - Resiliencia
Sem tratamento de conflito entre sessoes
Dois usuarios editam o mesmo objeto. Quem ganha? Nenhum
Falha silenciosa Dados sobrescritos Conflito de sessao

Em mashups com multiplos usuarios ou abas concorrentes, dois processos podem tentar modificar o mesmo objeto quasi-simultaneamente. O QIX Engine rejeita modificacoes concorrentes com codigo de erro especifico (qError code 6 - conflict). Sem tratamento, a Promise e rejeitada silenciosamente e o usuario nao ve nenhum erro.

Errado - falha invisivel 
// Sem try/catch: erro engolido
obj.setProperties(newProps);

// Se outro usuario estava editando:
// - Promise rejeitada com code 6
// - Nenhum feedback para o usuario
// - Suas mudancas silenciosamente perdidas
// - App continua como se tivesse funcionado
Correto - com retry automatico 
const setWithRetry = async (obj, getChanges, max = 3) => {
  for (let attempt = 0; attempt < max; attempt++) {
    try {
      const fresh = await obj.getProperties();
      const updated = getChanges(fresh);
      await obj.setProperties(updated);
      return; // sucesso
    } catch (err) {
      if (err.qErrCode === 6 && attempt < max - 1) {
        // conflito: aguarda e tenta novamente
        await new Promise(r => setTimeout(r, 100));
        continue;
      }
      throw err; // erro nao recuperavel
    }
  }
};

Uso do padrao de retry

// Passa uma funcao que sabe como aplicar as mudancas
await setWithRetry(obj, (currentProps) => {
  // currentProps sempre tem o estado mais recente
  return {
    ...currentProps,
    title: 'Dashboard Atualizado',
    qHyperCubeDef: {
      ...currentProps.qHyperCubeDef,
      qDimensions: newDimensions
    }
  };
});

// Se outro usuario editou entre as tentativas,
// a funcao recebe as props atualizadas e re-aplica
📚
Sobre o qErrCode 6: Este codigo indica que o objeto foi modificado por outra sessao desde o seu ultimo getProperties. O padrao de retry com re-fetch garante que voce sempre aplica suas mudancas sobre o estado mais recente, evitando a condicao de corrida.
