Todo mundo fala de AI Agents para dados. Poucos falam do que impede esses agentes de funcionar bem. O problema quase sempre e o mesmo: o agente consultou a tabela errada, com o campo errado, e entregou um numero que nao existe.

O problema que mata o AI Agent antes de comecar

Imagine que voce conecta um AI Agent ao seu data warehouse. O agente tem acesso a todas as tabelas. Alguem pergunta: "Qual foi a receita liquida do mes passado?"

O agente olha as tabelas disponíveis e encontra: fct_ord_v3, fct_ord_legacy, ord_all_regions_tmp. Ele nao sabe qual usar. Nao sabe se val_liquido ou net_revenue_usd e o campo correto. Nao sabe se a logica de "liquido" ja desconta devolucoes ou nao.

Resultado: o agente chuta. E provavelmente erra.

Sem camada semantica
-- O que o agente ve:
fct_ord_v3
fct_ord_legacy
ord_all_regions_tmp

-- Campos disponiveis:
val_liquido
net_revenue_usd
receita_bruta
valor_final_v2

-- Decisao do agente: adivinha.
Resposta imprecisa ou errada
Com camada semantica
-- O que o agente ve:
MEDIDA: Receita Liquida
Fonte:  fct_ord_v3.val_liquido
Filtro: status NOT IN ('cancelado')
Descricao:
  Receita apos devolucoes.
  Exclui pedidos cancelados.

-- Decisao do agente: certeira.
Resposta confiavel e governada

A diferenca nao esta no AI Agent. Esta em o que o agente consegue enxergar antes de responder. E isso e exatamente o que a camada semantica resolve.

O que e a camada semantica no contexto Qlik

No Qlik Cloud, a camada semantica nao e um produto separado. E um conjunto de configuracoes que voce ja tem disponíveis e que transforma nomes tecnicos em contexto de negocio.

📐

Master Dimensions

Dimensoes curadas com nome amigavel, descricao e classificacao. Quando um agente busca "Regiao", ele encontra a dimensao certa, nao o campo bruto cd_reg_v2.

📊

Master Measures

Metricas com expressao, formato e descricao. "Receita Liquida" e definida uma vez, usada em todos os graficos e por todos os agentes.

🔗

Business Logic

Configuracao que define como campos se relacionam, quais sao medidas vs. dimensoes, e como agrupar campos em conceitos de negocio. E o "vocabulario" que o Qlik Answers usa.

🤖

Logical Model

O modelo que o Qlik Answers indexa para responder perguntas em linguagem natural. So campos com classificacao correta e visibilidade ativa sao incluidos.

Esses quatro elementos juntos formam a camada semantica do Qlik Cloud. Cada um e configuravel. Nenhum requer infraestrutura adicional.

Arquitetura: dbt + Qlik + AI Agents

Quando voce conecta o dbt ao Qlik Cloud (como vimos na Semana 15), a camada semantica fica entre os dois lados: os dados transformados que chegam do warehouse e os agentes de IA que vao consumi-los.

Fontes brutas
→
dbt (modelos + metricas)
→
Data Warehouse
↓

Repare que dashboards e AI Agents consomem o mesmo modelo semantico. Isso garante que a "Receita Liquida" do dashboard seja identica a "Receita Liquida" que o agente calcula. Uma unica fonte de verdade para humanos e maquinas.

Qlik Business Logic na pratica

O Business Logic e configurado via interface no Qlik Cloud (menu do app), mas voce tambem pode exportar e versionar a configuracao como JSON. Veja o que cada secao controla:

business-logic-config.json (estrutura simplificada)
// Classificacao de campos
{
  "fieldAttributes": [
    {
      "name": "val_liquido",
      "businessName": "Receita Liquida",
      "description": "Receita apos devolucoes e cancelamentos",
      "type": "measure",
      "visibility": "visible",
      "defaultAggregation": "Sum"
    },
    {
      "name": "nm_regiao",
      "businessName": "Regiao",
      "description": "Regiao geografica do pedido",
      "type": "dimension",
      "visibility": "visible"
    },
    {
      "name": "cd_interno_produto",
      "visibility": "hidden"
      // campos internos ficam ocultos para agentes
    }
  ],

  // Grupos de conceito
  "conceptGroups": [
    {
      "name": "Financeiro",
      "fields": [
        "val_liquido",
        "val_bruto",
        "val_devolvido"
      ]
    }
  ]
}

O que acontece sem essa configuracao

O Qlik Answers indexa todos os campos do app por padrao, incluindo chaves tecnicas, flags internos e colunas temporarias. O agente de IA fica confuso com nomes como flg_ativo_v2, dt_carga_etl, cd_hash_linha. Campos que nao fazem sentido para perguntas de negocio nunca deveriam chegar ao modelo semantico.

Armadilha mais comum

Ativar o Qlik Answers antes de configurar o Business Logic. O agente vai indexar tudo, incluindo campos tecnicos que ele nao sabe interpretar. O resultado sao respostas imprecisas ou perguntas que o Qlik Answers "nao consegue responder" mesmo com os dados certos no app. Configure o Business Logic primeiro. Sempre.

Master Items como contrato entre BI e AI

Master Dimensions e Master Measures sao a camada mais visivel da semantica no Qlik. Ao criar um Master Measure, voce define a expressao uma vez e ela fica disponível para:

Dashboards criados por qualquer analista, Qlik Answers ao responder perguntas em linguagem natural, e futuras integrações com agentes externos via API.

Qlik Script: criando Master Measure via automacao
// Via Qlik Engine API (JSON-RPC)
{
  "method": "CreateMeasure",
  "params": {
    "qProp": {
      "qInfo": {
        "qType": "measure"
      },
      "qMeasure": {
        "qLabel": "Receita Liquida",
        "qDef": "Sum({<status_pedido-={'Cancelado','Devolvido'}>} val_liquido)",
        "qDescription": "Receita apos exclusao de pedidos cancelados e devolvidos"
      },
      "qMetaDef": {
        "tags": ["financeiro", "kpi"]
      }
    }
  }
}

Quando o Qlik Answers recebe a pergunta "Qual foi a receita liquida de outubro?", ele busca no Logical Model a medida com label "Receita Liquida" e executa exatamente essa expressao. Nao improvisa. Nao recalcula de outra forma. Usa o que voce definiu.

dbt Semantic Layer como fonte de verdade pre-Qlik

Se voce ja usa dbt (como vimos na Semana 15), pode ir um passo alem: definir as metricas no dbt com MetricFlow e usar o warehouse como ponte para o Qlik. A vantagem e que as definicoes ficam em um lugar so e versionadas em Git.

dbt/models/marts/schema.yml (definicao de metrica)
semantic_models:
  - name: pedidos
    description: Modelo semantico de pedidos
    model: ref('mart_orders')
    defaults:
      agg_time_dimension: data_pedido

    entities:
      - name: pedido
        type: primary
        expr: order_id

    dimensions:
      - name: regiao
        type: categorical
        expr: nm_regiao
      - name: data_pedido
        type: time
        type_params:
          time_granularity: day

    measures:
      - name: receita_liquida
        description: Receita apos cancelamentos e devolucoes
        agg: sum
        expr: total_order_value
        create_metric: true

metrics:
  - name: receita_liquida
    label: Receita Liquida
    description: KPI principal de faturamento
    type: simple
    type_params:
      measure: receita_liquida
    filter: {{ Dimension('pedido__status') }} not in ('Cancelado', 'Devolvido')

O Qlik Cloud consome essa definicao via QVD exportado do warehouse. O load script (ja enxuto depois do dbt) lê o resultado e popula o modelo. O Business Logic do Qlik mapeia o campo receita_liquida para o nome de negocio correto.

O fluxo completo em tres linhas

Load script pos-dbt (enxuto)
// Qlik Cloud load script depois que o dbt fez o trabalho pesado

MART_ORDERS:
LOAD
    order_id            AS [ID Pedido],
    nm_regiao           AS [Regiao],
    data_pedido         AS [Data Pedido],
    receita_liquida     AS [val_liquido]
FROM [lib://QVD/mart_orders.qvd]
(qvd);
// Business Logic e Master Measures fazem o resto.
// O agente consulta "Receita Liquida". Recebe exatamente isso.

4 armadilhas ao configurar a camada semantica para AI Agents

1

Deixar campos tecnicos visiveis no Logical Model

Campos como dt_carga_etl, sk_hash, flg_ativo nao tem sentido para perguntas de negocio. Se ficarem visiveis, o agente vai tenta-los e errar. Regra: se o analista de negocio nao usa o campo em um dashboard, o campo deve ser hidden no Business Logic.

2

Ter a mesma metrica com nomes diferentes

"Receita", "Faturamento" e "Revenue" no mesmo app criam ambiguidade para o agente. Ele nao sabe qual usar e pode misturar. Defina um unico nome canonico para cada metrica e use synonyms no Business Logic para mapear variacoes.

3

Nao classificar campos como medida ou dimensao

Sem classificacao, o Qlik Answers precisa inferir pelo tipo de dado. Inferencia erra: campos numericos de ID podem virar medidas, datas podem virar dimensoes incorretas. Classificar explicitamente e a diferenca entre um agente que entende o modelo e um que chuta.

4

Ignorar o Logical Model Group

Master Items com visibilidade correta nao sao indexados automaticamente se nao estiverem em um Logical Model Group. Este e o erro mais silencioso: o Business Logic parece configurado, mas o Qlik Answers responde como se os dados nao existissem. Verifique se o grupo esta ativo e inclui os itens certos.

O que muda na pratica

Em um app real com mais de 80 campos, configurar a camada semantica antes de ativar o Qlik Answers produziu resultados mensuraveis:

87%
perguntas respondidas com precisao pelo Qlik Answers
23
campos visiveis (de 80+ campos tecnicos no modelo)
0
ambiguidades de metrica reportadas pelos usuarios

O filtro agressivo (23 campos de 80+) foi a decisao mais importante. Menos opcoes para o agente significa menos chance de escolha errada. Camada semantica boa e camada semantica enxuta.

Checklist: camada semantica pronta para AI Agents

✓
Todos os campos tecnicos (chaves, flags, hashes) estao marcados como hidden no Business Logic
✓
Cada medida tem businessName e description em linguagem de negocio
✓
Dimensoes e medidas estao classificadas explicitamente (nao inferidas)
✓
Logical Model Group criado e ativo, contendo os Master Items corretos
✓
Nao ha duplicatas de nomes de metrica no mesmo app
✓
Sinonimos configurados para termos alternativos do negocio
✓
Testado com ao menos 10 perguntas reais antes de abrir para usuarios

A camada semantica e a base. Nao o topo.

Antes de ativar qualquer AI Agent sobre seus dados, pergunte: o que ele vai enxergar? Se a resposta for "as tabelas brutas do warehouse", o agente vai errar. Se a resposta for "uma camada semantica governada", o agente vai acertar.

Qlik Answers, Copilot, agentes externos via API: todos dependem do mesmo principio. Dados sem contexto nao sao conhecimento. Sao ruido.
