Section 01 - The Starting Point

Qlik is powerful. But it has real gaps.

Every team that moves beyond basic Qlik Cloud usage hits the same walls. Not because the platform is lacking - but because no BI tool can anticipate every enterprise need out of the box.

What native Qlik delivers
  • Basic straight table with sort and simple export
  • Objects disconnected from external systems
  • Documentation outside the app (Confluence, Wiki)
  • Support reported outside the analytical context
  • Fixed toolbar, no customization
What Qore extensions solve
  • Enterprise table with real pagination, presets, and freeze
  • ServiceNow ticket created inside Qlik with full app context
  • Live documentation embedded in the dashboard itself
  • Insight suite with auto-discovery of KPIs and data model
  • Native-style buttons injected into the Qlik Cloud toolbar
💡
What are Qlik Cloud extensions? Custom visualizations built in JavaScript (RequireJS AMD) that run inside Qlik as native objects - with full access to the QIX Engine, Engine API, app properties, and user context. Unlike mashups, they live inside the app, not outside it.
Section 02 - Extension 1
📊
Qore Straight Table
v1.0.34 · ~2,200 lines of code · 9 files
Real pagination via QIX Engine Visual presets CSV + PDF export Alternate States Column freeze

The most requested object by analysts at every Qlik enterprise. Native works - but for real data at enterprise scale, it falls short.

The problem it solves

Qlik's native Straight Table loads data with infinite scroll and client-side pagination - which in practice means exporting only what's visible, not the full dataset. View presets don't exist. Column freeze, same story.

How Qore Straight Table works

The fundamental difference is pagination via the QIX Engine: instead of loading everything and filtering client-side, the extension sends qTop/qHeight calls directly to the Engine - respecting the 10,000-cell limit per request and making multiple trips when needed.

// Real pagination - never client-side row hiding
return ext.backendApi.getData([{
  qTop: top,
  qLeft: 0,
  qWidth: totalCols,
  qHeight: safeHeight  // floor(10000 / totalCols)
}]);
For the Analyst

Visual presets

Admin defines pre-configured views (columns, filters, sort, freeze). Users save their own views per browser. No Engine round-trip to switch between them.

For the Developer

applyPatches, not setProperties

Every mutation uses applyPatches with qSoftPatch=false to avoid desyncing qInterColumnSortOrder - a bug that breaks other objects on the same sheet.

⚙️
Engineering note: Qlik Cloud blocks navigator.clipboard inside iframes. Copy/paste between Qore tables uses localStorage as an internal channel - transparent to the user, no loss of functionality.
Section 03 - Extension 2
📖
Qore Info Page
v2.28 · Singleton · Auto Discovery
Embedded documentation KPI auto-discovery Live data model Replaces Confluence/Wiki

App documentation that lives inside Qlik - not in an outdated wiki nobody reads.

The problem it solves

In any enterprise with multiple Qlik apps, dashboard documentation exists somewhere in Confluence or SharePoint - outdated, hard to find, completely disconnected from the analyst actually looking at the data right now.

How it works in practice

Adding the extension to any sheet injects an "About" button into Qlik Cloud's native toolbar - next to the Bookmarks button, using the same MUI design. One click opens a modal with configurable tabs:

  • About - Markdown app description with responsible contacts
  • KPIs - featured master measures with descriptions and formulas
  • Sheets - list of all published sheets in the app
  • Data Model - tables and keys read directly via enigma.getTablesAndKeys
  • Auto - everything above generated automatically, no admin typing required
🔍
Auto Discovery in 4 parallel calls: The Auto tab runs app.getList('sheet'), getList('MeasureList'), getList('DimensionList'), and enigmaModel.getTablesAndKeys() simultaneously - delivering a complete app snapshot with zero manual configuration.

Singleton pattern

The extension uses window.__qoreInfoPageInstance to guarantee a single instance per app - regardless of how many sheets contain the object. A 2-second setInterval monitors whether the About button was removed by Qlik's navigation and re-injects it automatically.

Section 04 - Extension 3
🎫
Qore Support Ticket
v3.54 · ServiceNow · Qlik Automation Webhook
ServiceNow integrated Automatic app context Hypercube-driven lookups Smart prefill

The analyst found a wrong number. Instead of opening another tab, taking screenshots, and describing context from scratch - they file a ticket directly from Qlik, with context filled in automatically.

The problem it solves

Every company using Qlik for critical data faces the same issue: an analyst spots an anomaly, doesn't know if it's bad data or a business rule, and the reporting process is slow and context-free. Result: bugs that take weeks to fix because nobody can reproduce them.

Integration architecture

The extension injects a "Report Issue" button in the toolbar (same MUI pattern as Info Page). The form uses the app's own data model to populate dropdowns - no external endpoints, no separate maintenance:

// Assignee lookup directly from the app's data model
cubeLookup.searchAsync(props.lookups.assignTo, query)
// → createSessionObject({qDimensions: [keyField, labelField]})
// → filters by search term, returns matching rows

The payload sent to ServiceNow via Qlik Automation includes automatic context - the analyst doesn't have to describe where they were:

{
  "u_qlik_app": "app.id",
  "u_qlik_sheet": "current sheet at time of click",
  "u_caller_email": "via getAuthenticatedUser()",
  "u_browser": "navigator.userAgent"
}
📈
4-version evolution: Data lookups went from hard-coded lists (v3.22) to separate REST endpoints (v3.39) to a combined endpoint (v3.40) to the current session hypercubes (v3.43) - eliminating any external service and using Qlik's data model directly.

Section 06 - For Developers

Patterns that make extensions enterprise-grade

What separates an extension that works in a demo from one that survives production with hundreds of concurrent users.

1. Singleton Pattern

Global extensions (Info Page, Support Ticket) use a window-keyed instance to guarantee a single instance, regardless of how many sheets contain the object:

if (window['__qoreInfoPageInstance']) {
  window['__qoreInfoPageInstance'].layout = layout;
  return; // already initialized - update state only
}
// First call: full bootstrap
window['__qoreInfoPageInstance'] = { layout, ctx, destroy };

2. Toolbar Injection (MUI Clone)

Instead of rebuilding Qlik Cloud's design from scratch, extensions clone the MUI wrapper of the Bookmarks button and replace only the inner button - guaranteeing automatic visual compatibility with platform updates:

var bm = document.querySelector('[data-tid="assets-button-bookmarks"]');
var wrap = bm.parentNode.cloneNode(true);    // clone MUI wrapper
var freshBtn = wrap.querySelector('button').cloneNode(false);
freshBtn.innerHTML = QORE_ICON_16;
freshBtn.addEventListener('click', onOpen);
bm.parentNode.insertBefore(wrap, bm.nextSibling);

3. applyPatches, never setProperties for hypercubes

Using setProperties to modify dimensions and measures can desync qInterColumnSortOrder with the new array - the Engine throws "Invalid sort order" and other objects on the sheet break. The solution: applyPatches with explicit sort order normalization after each mutation.

⚠️
10,000-cell limit: Qlik Cloud caps getData at 10,000 cells per request. For a 20-column table, that means at most 500 rows per call. Qore Straight Table computes safePageSize = floor(10000 / totalCols) and makes multiple trips when needed - transparent to the user.
Section 07 - The Core Point

Extensions aren't workarounds. They're the platform.

There's a common belief that customizing a BI tool with extensions signals a platform limitation. The correct perspective is the opposite: Qlik Cloud was designed to be extensible. The Engine API, the property system, RequireJS AMD support - all of this is first-class infrastructure for building exactly what the enterprise needs.

What the Qore Extension Framework demonstrates is that it's possible to build extensions that:

  • Survive platform updates (MUI clone, robust selectors)
  • Scale to hundreds of concurrent users (singleton, correct Engine API usage)
  • Integrate with external systems without fragile dependencies (cube-driven lookups)
  • Maintain the same UX level as native Qlik (toolbar injection, edit-mode gating)
  • Evolve safely (applyPatches, sort order normalization)

The gap between what Qlik delivers out of the box and what the enterprise actually needs isn't a problem. It's an opportunity to build differentiated value - directly in the platform where decisions happen.
