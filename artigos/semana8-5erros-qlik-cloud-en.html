Week 8 · Qlik Cloud Migration

The 5 Most Common Mistakes in Qlik Cloud Migration
(and How to Avoid Each One)

What nobody tells you before you hit the migrate button

I have been through dozens of Qlik Cloud migration projects. The successful ones were not the ones with the biggest budgets. They were the ones where the team knew the pitfalls before falling into them. Here are the five mistakes that appear in nearly every project, along with what to do to avoid them.

The 5 Mistakes

1
Migrating without auditing the data model first

QlikView accumulates years of patches, duplicate fields, obsolete QVDs, and joins that "nobody knows why they exist but nobody removes." Carrying that technical debt into Qlik Cloud does not clean it up. It multiplies it. You spend the same migration effort and arrive on the other side with the same anomalies, now on a new platform.

⚠️

Unused fields consume memory and increase licensing costs in Qlik Cloud's SaaS pricing model. Every unnecessary field has a price tag.

How to avoid it

Run a QlikView Audit before starting the migration. List all tables, fields, and QVDs. Document who owns what. Remove anything that has no clear owner. Arrive at Qlik Cloud with a data model that is 30% leaner than the original.

2
Going Big Bang: migrating everything at once

Project pressure often pushes teams to move all apps at the same time. It looks efficient on paper. In practice, when something breaks, you have no idea what caused it because everything changed simultaneously. Rolling back becomes a nightmare.

Recommended approach: wave-based migration
Wave 1 (Weeks 1-4):
  - Low-criticality apps
  - Validate environment, permissions, connectors
  - Train the technical team on the new platform

Wave 2 (Weeks 5-10):
  - Mid-criticality operational apps
  - Adapt load script patterns for Qlik Cloud
  - Validate query performance

Wave 3 (Weeks 11-16):
  - Critical production apps (financial BI, executive dashboards)
  - Parallel run: QlikView and Qlik Cloud side by side
  - KPI validation before the final switch
How to avoid it

Segment the migration into waves by criticality. Always start with what hurts the least if it breaks. Use the parallel run to validate critical KPIs before decommissioning QlikView.

3
Ignoring Set Analysis behavioral differences between QlikView and Qlik Cloud

This is the most technical mistake and one of the most dangerous. Some Set Analysis expressions behave differently in Qlik Sense and Qlik Cloud, especially when they involve calculated flags, alternate states, and expressions inside sets. Critical KPIs can return wrong numbers without generating any visible error.

Example of an expression that may behave differently
// QlikView: works as expected in most contexts
Sum({<Year={$(=Max(Year))}>} Revenue)

// Qlik Cloud / Qlik Sense: same expression, same intent,
// but Dollar Sign Expansion behavior inside the Set
// can diverge depending on the object's context.
// Always validate with real data before going to production.
How to avoid it

Build a catalog of critical expressions before migrating. For each important KPI, document the expected value using a test dataset. After migration, run a validation batch comparing QlikView vs. Qlik Cloud results with the same data.

4
Forgetting change management for end users

The technical team migrates the apps. End users open Qlik Cloud for the first time and do not recognize anything. The interface changed, the menu is gone, the button they always used to export is now somewhere else. The predictable outcome: resistance, support tickets, and requests to "go back to the old system."

A platform migration without a culture migration is half a project. The second half will be the most expensive one.

How to avoid it

Plan at least four weeks of communication before the switch. Run training sessions segmented by user profile (consumer, author, administrator). Create a quick reference guide for "what changed and where to find it." Designate champions within each business area.

5
Underestimating the impact of custom extensions

Extensions built for QlikView or on-premise Qlik Sense frequently do not work in Qlik Cloud. The SaaS environment has stricter security restrictions, the API has changed across several versions, and some extensions depend on features that simply no longer exist.

Discovering this the week of go-live is a recipe for delaying the project by at least one month.

How to avoid it

Inventory all custom extensions at the start of the project. For each one: test it in the Qlik Cloud environment, document what works and what breaks. Evaluate whether to replace it with an equivalent native visualization, rewrite it to the new standard, or remove it entirely. Reserve at least four weeks for this in the project timeline.

The pattern behind all five mistakes

Looking at all five together, the pattern is the same: they are all problems of insufficient planning, not insufficient technical skill. The team knows how to migrate. What is missing is discovering the pitfalls before tripping over them.

Successful migration projects invest 30% to 40% of the total timeline in preparation before moving the first app. That sounds like a lot. But it is less than the rework that comes later when you skip that phase.

Migrating to Qlik Cloud is not optional. QlikView is end-of-life. The SaaS NPrinting path already has mandatory transition dates. The question is not whether you will migrate, but how you will do it without turning the project into a crisis.
