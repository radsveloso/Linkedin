Set Analysis Avançado no Qlik Cloud:
as expressões que a maioria dos analistas não usa (mas deveria)

Da sintaxe básica ao que separa os analistas sênior dos demais

Se você sabe usar {<Year={2024}>}, está usando aproximadamente 20% do que o Set Analysis pode fazer. Os outros 80% são o que separa um dashboard que "funciona" de um que surpreende — em performance, flexibilidade e capacidade analítica. Este artigo cobre as cinco técnicas que eu mais vejo analistas não dominando, mesmo depois de anos com Qlik.

Estimativas baseadas em projetos de otimização de dashboards 2022-2024

As 5 Técnicas Avançadas

1
Intermediário
Dollar Sign Expansion dentro do Set

A maioria usa valores fixos dentro de sets: {<Year={'2024'}>}. O problema é que isso não é dinâmico — quando chega 2025, alguém tem que atualizar a expressão manualmente. A solução é Dollar Sign Expansion: deixar o Qlik calcular o valor no momento da renderização.

Evolução: fixo → dinâmico
// ❌ Fixo — requer manutenção manual todo ano
Sum({<Year={'2024'}>} Revenue)

// ✅ Dinâmico — sempre calcula o ano máximo disponível
Sum({<Year={$(=Max(Year))}>} Revenue)

// ✅ Ano anterior dinâmico
Sum({<Year={$(=Max(Year)-1)}>} Revenue)

// ✅ Últimos 12 meses a partir da data mais recente
Sum({<Date={">=$(=MonthStart(Max(Date),-11))"}>} Revenue)
⚠️

No Qlik Cloud, o comportamento do Dollar Sign Expansion dentro de sets pode divergir do QlikView quando há expressões complexas com múltiplos campos calculados. Sempre valide com dados reais antes de ir para produção.

Ponto de atenção

O Dollar Sign Expansion é avaliado antes da expressão de Set Analysis ser processada. Isso significa que ele sempre retorna um valor único, não uma lista. Para selecionar múltiplos valores dinamicamente, use a Técnica 3 (Aggr).

2
Intermediário
Operadores de conjunto: interseção, exclusão e adição que poucos dominam

O Set Analysis tem três operadores lógicos que a maioria desconhece ou nunca usa na prática: interseção (*), exclusão (-) e adição (+). Eles permitem combinar condições de forma muito mais elegante do que aninhando IF().

Operadores de conjunto na prática
// INTERSEÇÃO (*): clientes que compraram E estão ativos
Sum({<CustomerID=P({<Year={$(=Max(Year))}>} CustomerID)>
  * <Status={'Active'}>} Revenue)

// EXCLUSÃO (-): tudo exceto devoluções e cancelamentos
Sum({1 - <TransactionType={'Return','Cancel'}>} Revenue)

// ADIÇÃO (+): combinar dois grupos distintos
Sum({<Region={'South'}> + <Region={'North'}>} Revenue)

// EXCLUIR seleção atual do usuário para um campo
Sum({<Country=>} Revenue)
// o campo vazio remove a seleção de Country
Uso real

A exclusão de seleção {<Country=>} é especialmente útil para criar totais que ignoram o filtro do usuário — o equivalente a ALL() no DAX, mas com mais flexibilidade.

3
Avançado
Aggr() dentro de sets: segmentações que o modelo de dados não previu

Esta é a técnica que mais vejo analistas aprenderem errado. Aggr() dentro de um Set Analysis permite criar seletores dinâmicos baseados em agregações — ou seja, você pode selecionar "clientes cujo faturamento total no último ano foi acima de R$ 1 milhão" diretamente na expressão, sem criar campos auxiliares.

Aggr() como seletor dinâmico
// Seleciona clientes com faturamento > 1 milhão no ano
Sum({<CustomerID={"=Aggr(Sum({<Year={$(=Max(Year))}>} Revenue),CustomerID)>1000000"}>} Revenue)

// Top 10% de produtos por volume de vendas
Sum({<ProductID={"=Aggr(Sum(Qty), ProductID)>=$(=Fractile(Aggr(Sum(Qty),ProductID),0.9))"}>} Revenue)

// Clientes que compraram nos últimos 30 dias
Count({<CustomerID={"=Aggr(Max(SaleDate),CustomerID)>=$(=Today()-30)"}>} CustomerID)
⚠️

Expressões com Aggr() dentro de sets são computacionalmente pesadas. Em modelos com milhões de registros, avalie se o resultado pode ser pré-calculado como campo derivado no script de carga. O custo de processamento acontece a cada renderização do objeto.

Por que isso importa

Sem essa técnica, você precisaria criar um campo "flag" no script (IsHighValueCustomer = 1/0) toda vez que quiser uma segmentação assim. Com Aggr() no set, você faz isso diretamente na expressão, sem recarregar os dados.

4
Avançado
Alternate States: comparações entre contextos sem duplicar dados

Alternate States é um recurso que permite criar múltiplos contextos de seleção independentes dentro do mesmo app. O caso de uso mais clássico é a comparação período A vs. período B — mas o recurso vai muito além disso.

Set Analysis com Alternate States
// Contexto padrão (seleção do usuário)
Sum(Revenue)

// State "PeriodoA" — independente da seleção atual
Sum({PeriodoA} Revenue)

// State "PeriodoB" com override de campo específico
Sum({PeriodoB <Year={$(=Max({PeriodoB} Year))}>} Revenue)

// Variação percentual entre os dois states
(Sum({PeriodoA} Revenue) - Sum({PeriodoB} Revenue))
/ Sum({PeriodoB} Revenue)
💡

No Qlik Cloud, os Alternate States são configurados em: Folha → Editar → Estados do app. Você pode criar até 125 states por app. Cada objeto pode ser associado a um state diferente — ou usar o state padrão.

Caso de uso real

Compare o desempenho de duas regiões geograficas com filtros completamente independentes, ou analise o impacto de uma promoção num segmento sem afetar os filtros globais do dashboard.

5
Expert
Set Analysis vs. IF(): quando cada um destrói a performance do outro

Esta é a discussão que mais gera dúvida em revisões de código. A regra geral é: IF() filtra linhas uma por vez; Set Analysis filtra o conjunto antes de agregar. A diferença de performance pode ser dramática em grandes volumes.

❌ IF() — lento em volume
Sum(
  If(Year = Max(Year),
    Revenue
  )
)
// Avalia IF() em cada linha
// antes de agregar
✅ Set Analysis — rápido
Sum(
  {<Year={$(=Max(Year))}>}
  Revenue
)
// Filtra o conjunto primeiro
// depois agrega

Quando usar IF() mesmo assim: quando a condição depende de valores calculados dinamicamente no contexto da linha (como comparar a linha atual com a linha anterior), ou quando você precisa de granularidade por linha individual.

IF() válido: cálculo linha a linha
// Este caso não tem equivalente direto em Set Analysis
// porque depende da relação entre linhas vizinhas
Sum(If(Revenue > Above(Revenue), Revenue - Above(Revenue), 0))

O que muda no Qlik Cloud vs. QlikView

A maioria das técnicas acima funciona em ambos os ambientes, mas há diferenças que causam resultados inesperados na migração:

Dollar Sign Expansion em contextos de objeto: no Qlik Cloud, a avaliação do DSE dentro de sets pode variar dependendo se o objeto está num container ou numa extensão customizada. Sempre teste expressões migradas com datasets reais.

Alternate States e extensões: extensões desenvolvidas para Qlik Sense on-premise podem não respeitar Alternate States no Qlik Cloud SaaS. Verifique a compatibilidade de cada extensão antes de depender de states em produção.

Performance de Aggr() em SaaS: o modelo de execução do Qlik Cloud pode comportar-se diferente do servidor on-premise em expressões com Aggr() aninhado. Monitore o consumo de memória dos objetos mais complexos usando o Activity Monitor do Qlik Cloud Management Console.
