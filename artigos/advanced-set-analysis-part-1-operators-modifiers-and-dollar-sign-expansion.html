1. Complete Anatomy of a Set Analysis Expression

Before advancing to complex patterns, you need to master the exact anatomy. Every part of a Set Analysis expression has a specific role - and confusing them is the source of 90% of bugs.

Full structure

Sum( { set_identifier  < set_modifier > }  expression )
      ^                ^               ^
      |                |               |
  Set identifier   Set modifier   Aggregation
                                   expression

Set Identifiers

1
{ 1 } - Full set (all records)Completely ignores user selections. Calculates across 100% of the data regardless of what has been filtered.
$
{ $ } - Current set (active selection)Equivalent to the expression without Set Analysis. Represents exactly what the user has selected. The starting point for modifiers.
_
{ $_1 } - Previous selectionThe set representing the selection immediately before the current one. Useful for interactive "before and after" comparisons.
BM
{ BM01 } - Bookmark as setA saved bookmark can be used as a set identifier. Lets you express "sales in the state saved as BM01".
// Practical examples of identifiers
// Total sales - ignores any Region, Product, Year selection
Sum({1} Amount)

// Sales in current selection - identical to Sum(Amount) without Set Analysis
Sum({$} Amount)

// Sales under the previous selection
Sum({$_1} Amount)

// Sales under bookmark "BM01" state (e.g., Top 10 Customers)
Sum({BM01} Amount)

Critical distinction: {1} ignores ALL selections, including selections on the expression's own field. {$} respects the current selection. Picking the wrong identifier is the most silent and dangerous mistake in Set Analysis.

2. Set Operators

Set operators allow you to combine, subtract, intersect, and modify data sets with precision. They are the foundation of set algebra in Qlik - and what makes Set Analysis genuinely powerful.

Available operators
+Union - includes all elements from both sets
-Difference - elements in the first set that are not in the second
*Intersection - only elements present in both sets
/Symmetric difference - elements in one OR the other, but not both
+
Union Operator

Combines two sets: the result contains all elements from both. Equivalent to logical OR when applied to different subsets of the same field.


// Sales of Electronics OR Furniture (regardless of current selection)
Sum({<Category={'Electronics'}> + <Category={'Furniture'}>} Amount)

// More concise equivalent for the same field:
Sum({<Category={'Electronics', 'Furniture'}>} Amount)

// More powerful union: sets from different fields
// Current selection + November records from any year
Sum({$ + <Month={'November'}>} Amount)

// Real-world case: customers in the current selection OR VIP customers
Count({$ + <CustomerSegment={'VIP'}>} DISTINCT CustomerID)
-
Difference Operator

Returns the first set minus elements also in the second. Essential for exclusion analysis: "everything except X".


// All records EXCEPT returns
Sum({1 - <Status={'Return'}>} Amount)

// Current selection EXCEPT 'Product X'
Sum({$ - <Product={'Product X'}>} Amount)

// Real-world case: net revenue = gross minus cancellations and returns
Sum({1 - <TransactionType={'Cancellation', 'Return'}>} GrossAmount)

// All customers who did NOT buy last month (churn analysis)
Count({
  <CustomerID=P({1}<Month={$(=Month(Today()))}> CustomerID)>
  -
  <CustomerID=P({1}<Month={$(=Month(AddMonths(Today(),-1)))}> CustomerID)>
} DISTINCT CustomerID)
*
Intersection Operator

Returns only elements present in both sets simultaneously. Equivalent to logical AND between distinct sets.


// Customers who bought Electronics AND are in the current selection
Count({
  <CustomerID=P({1}<Category={'Electronics'}> CustomerID)>
  *
  $
} DISTINCT CustomerID)

// Real-world case: average ticket for customers who purchased
// BOTH in Q1 AND Q4 (seasonally recurring customers)
Avg({
  <CustomerID=P({1}<Quarter={'Q1'}> CustomerID)>
  *
  <CustomerID=P({1}<Quarter={'Q4'}> CustomerID)>
} OrderValue)
/
Symmetric Difference - The Forgotten Operator

Returns elements that are in one set OR the other, but not both. Useful for comparison analyses where you want to highlight what is exclusive to each set.


// Products sold in 2023 OR in 2024, but not in both
// (products that entered or left the portfolio)
Count({
  <ProductID=P({1}<Year={2023}> ProductID)>
  /
  <ProductID=P({1}<Year={2024}> ProductID)>
} DISTINCT ProductID)

3. Advanced Modifiers

Modifiers alter the active selection for a specific field within the set. They are expressed between < > and determine exactly which values of each dimension participate in the calculation.

Types of Modifiers

Direct assignment - literal values 

// Defines exactly which values
// the field must have in the set

Sum({<Year={2024}>} Amount)

Sum({<Region={'South', 'West'}>} Amount)

Sum({<Status={'Active'},
     Year={2024}>} Amount)

// Overrides the current field selection
// and uses the specified values
Exclusion modifier - removes field 

// Removes the selection from a specific field
// while keeping other field selections intact

// Ignore Year selection, keep the rest
Sum({<Year=>} Amount)

// Ignore both Month AND Quarter, keep others
Sum({<Month=, Quarter=>} Amount)

// Practical for "full-year total" within
// a context filtered by week

Modifier with Expression-Derived Value


// Current year derived from expression - dynamic, never needs updating
Sum({<Year={$(=Year(Today()))}>} Amount)

// Previous month calculated dynamically
Sum({<Month={$(=Month(AddMonths(Today(), -1)))},
     Year={$(=Year(AddMonths(Today(), -1)))}>} Amount)

// Dynamic period: from year start to today
Sum({<Date={">=$(=YearStart(Today()))<=$(=Today())"}>} Amount)

The difference between Year={2024} and Year={$(=Year(Today()))} seems small but is critical in production. The second always calculates the correct year, without needing to update the expression at each year boundary.

Modifiers with Partial Matching - Wildcards


// Products whose name starts with "Pro"
Sum({<Product={"Pro*"}>} Amount)

// Customers whose email is from the @company.com domain
Count({<Email={"*@company.com"}>} DISTINCT CustomerID)

// Records with code containing "US" in any position
Sum({<CountryCode={"*US*"}>} Amount)

4. Dollar-Sign Expansion in Set Analysis

Dollar-sign expansion $( ) is the mechanism that makes Set Analysis truly dynamic. It resolves the content of the expansion before Set Analysis is evaluated - allowing variables, expressions, and even other Set Analysis expressions to define the set parameters.

1
$(variable) - variable expansionSubstitutes the token with the current value of the variable. Happens before Set Analysis evaluation.
2
$(=expression) - expression expansionEvaluates the expression and uses the result as part of the Set Analysis. Enables dynamic calculations in set parameters.
3
$(#variable) - numeric expansionReturns the numeric value without regional formatting. Critical when thousand/decimal separators vary across locales.
// Pattern 1: variable as dynamic filter
// Script: SET vCurrentYear = Year(Today());
Sum({<Year={$(vCurrentYear)}>} Amount)
// Expands to: Sum({<Year={2025}>} Amount)

// Pattern 2: dynamic expression as parameter
Sum({<Date={">=$(=MonthStart(Today()))<=$(=Today())"}>} Amount)

// Pattern 3: variable containing a full Set Analysis expression
// Script: SET vVIPFilter = '{<CustomerSegment={''VIP''}>}';
Sum($(vVIPFilter) Amount)

// Pattern 4: numeric expansion to avoid locale issues
// Wrong (may break in different locales):
Sum({<Amount={>$(vTarget)}>} Orders)

// Correct - always returns the number without formatting:
Sum({<Amount={>$(#vTarget)}>} Orders)

Rule of thumb: whenever a modifier value comes from a numeric variable, use $(#variable) instead of $(variable). Prevents silent bugs in environments with regional settings different from the development environment.

5. P() and E() - Element Functions

The P() (Possible Values) and E() (Excluded Values) functions are the most sophisticated tools in Set Analysis. They allow you to use the set of possible or excluded values from one field as the parameter for another field - creating high-precision cross-field filters.

P() - Possible Values 

// P(field) returns the set of POSSIBLE
// (non-excluded) values of a field

// Customers possible in the current selection
P(CustomerID)

// Products possible in set {1} filtered by Category
P({1}<Category={'Electronics'}> ProductID)

// Use: filter ANOTHER field by the possible values
Sum({<CustomerID=P({1}<Region={'West'}> CustomerID)>} Amount)
E() - Excluded Values 

// E(field) returns the set of EXCLUDED
// (grayed out in Qlik) values of a field

// Use: calculate over what was excluded
Sum({<CustomerID=E(CustomerID)>} Amount)
// "Sales of customers who were excluded
//  by the current selection"

P() in Practice - Cohort Filtering


// Case 1: sales generated by customers who purchased a specific product
Sum({
  <CustomerID = P({1}<ProductID={'PROD-LAPTOP-001'}> CustomerID)>
} Amount)

// Case 2: cross-sell analysis
// How much do Electronics buyers also spend in Appliances?
Sum({
  <CustomerID = P({1}<Category={'Electronics'}> CustomerID),
   Category = {'Appliances'}>
} Amount)

// Case 3: cohort intersection - customers who bought in BOTH Q1 AND Q3
Count({
  <CustomerID =
    P({1}<Quarter={'Q1'}> CustomerID)
    *
    P({1}<Quarter={'Q3'}> CustomerID)
  >
} DISTINCT CustomerID)

// Case 4: new customers this year (bought now, NOT in previous year)
Sum({
  <CustomerID =
    P({1}<Year={$(=Year(Today()))}> CustomerID)
    -
    P({1}<Year={$(=Year(Today())-1)}> CustomerID)
  >
} Amount)

P() and E() are evaluated in the context of the set that wraps them. P({1} Field) and P({$} Field) produce completely different results: the first ignores the selection, the second respects it. Always be explicit about which context you want.

Review Checklist - Set Analysis Part 1

  • ✅
    Correct identifier: use {1} to ignore selections, {$} to respect them.
  • ✅
    Numeric dollar-sign: use $(#variable) when the modifier is numeric, to avoid locale bugs.
  • ✅
    Correct operator: + is union (OR), * is intersection (AND), - is exclusion.
  • ⚠️
    P() needs explicit context: never write P(Field) without specifying {1} or {$} inside.
  • ⚠️
    Double quotes for wildcards, single for strings: {"Pro*"} for wildcard, {'Product A'} for literal value.
  • ℹ️
    Test with a small dataset: before using complex operators in production, validate with a reduced dataset where you know the expected result.
