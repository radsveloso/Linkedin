Performance Tuning Qlik Sense: Diagnóstico e Otimização de Ponta a Ponta

Por Rafael Veloso • 24 de maio de 2026
## Diagnóstico Antes de Otimização Antes de qualquer mudança, você precisa saber **onde está o gargalo**. Qlik Sense lento pode ter origem em quatro lugares distintos - e a solução para cada um é diferente. **1. Modelo de dados** - Synthetic keys ocultos, campos desnecessários em RAM, tabelas não normalizadas, NULLs não tratados. Causa a maioria dos problemas de reload lento e consumo de memória excessivo. **2. Script de carga** - Ausência de camada QVD, reloads completos onde deveria ser incremental, ordem ineficiente de LOADs, joins desnecessários. Impacta diretamente o tempo de reload. **3. Expressões e gráficos** - IF() onde deveria ser Set Analysis, AGGR() mal aplicado, cálculos complexos repetidos sem uso de variáveis, sheets sobrecarregados. **4. Infraestrutura** - Sizing incorreto de servidor, usuários simultâneos sem throttling, ausência de ODAG para datasets grandes. > "Otimizar expressão em um app com synthetic key não resolvido é pintar a parede de uma casa com fundação rachada." ### Como Ler o Log de Reload O primeiro passo de qualquer tuning é ler o log de reload. No Qlik Cloud: Data Integration > Spaces > [app] > Reload History. ``` 0001 LOAD statement: 2.450.000 rows in 4.2s 0002 Synthetic key warning: [OrderID, ProductID] ← ALERTA CRÍTICO 0089 Finished reload. Duration: 00:04:32 RAM peak: 8.4 GB Fields: 847 ← muitos campos = problema ``` --- ## 1. Modelo de Dados ### Synthetic Keys: Detecção e Correção Synthetic keys são criados quando duas ou mais tabelas compartilham mais de um campo com o mesmo nome. Cada synthetic key gera uma tabela intermediária invisível que consome memória e degrada performance. **Problema - cria synthetic key:** ``` Pedidos: LOAD OrderID, ProductID, CustomerID, Amount FROM pedidos.qvd (qvd); Produtos: LOAD ProductID, OrderID, ProductName, Category FROM produtos.qvd (qvd); // OrderID E ProductID presentes nas duas tabelas = synthetic key ``` **Solução - alias para desambiguar:** ``` Pedidos: LOAD OrderID, ProductID, CustomerID, Amount FROM pedidos.qvd (qvd); Produtos: LOAD ProductID, OrderID AS PedidoRef, // alias elimina o synthetic key ProductName, Category FROM produtos.qvd (qvd); ``` ### DROP FIELDS - Libere Memória Imediatamente Todo campo carregado ocupa RAM durante o reload e em uso. Campos não usados em nenhum gráfico são desperdício puro. ``` // Seletivo - carrega apenas o necessário Vendas: LOAD VendaID, ClienteID, ProdutoID, Valor, DataVenda, Regiao FROM vendas.qvd (qvd); // Alternativa: DROP após LOAD * DROP FIELDS ETLTimestamp, BatchID, InternalRef, LegacyCode; ``` Resultado típico: 40-60% de redução de RAM com esta ação isolada. ### Star Schema vs Snowflake O Qlik Sense é otimizado para star schema. Modelos snowflake aumentam joins internos e degradam performance. Desnormalize no script de carga. ``` // Star schema - desnormalizar no script DimProduto: LOAD p.ProductID, p.ProductName, c.CategoryName, s.SectorName FROM produtos.qvd (qvd) AS p JOIN categorias.qvd (qvd) AS c ON p.CategoryID = c.CategoryID JOIN setores.qvd (qvd) AS s ON c.SectorID = s.SectorID; ``` --- ## 2. Script e Camada QVD ### Incremental Load - Padrão Obrigatório em Produção Recarregar 10 milhões de linhas quando apenas 5.000 mudaram é o erro mais caro de performance. O padrão de incremental load resolve isso. ``` // BLOCO 1: Detectar a última data de carga LET vUltimaCarga = Peek('DataModificacao', -1, 'MaxData'); // BLOCO 2: Carregar delta ou full IF IsNull(vUltimaCarga) THEN // Primeira carga - full load Vendas_Delta: LOAD VendaID, ClienteID, ProdutoID, Valor, DataVenda, DataModificacao FROM [lib://DataSource/vendas.csv] (txt, utf8, embedded labels); ELSE // Carga incremental - apenas novos/alterados Vendas_Delta: LOAD VendaID, ClienteID, ProdutoID, Valor, DataVenda, DataModificacao FROM [lib://DataSource/vendas.csv] (txt, utf8, embedded labels) WHERE DataModificacao >= '$(vUltimaCarga)'; END IF // BLOCO 3: Mesclar delta com QVD existente Vendas: LOAD * FROM [lib://QVDs/vendas.qvd] (qvd) WHERE NOT EXISTS(VendaID); CONCATENATE(Vendas) LOAD * RESIDENT Vendas_Delta; DROP TABLE Vendas_Delta; STORE Vendas INTO [lib://QVDs/vendas.qvd] (qvd); ``` Ganho típico: 10x no tempo de reload em apps com histórico acima de 1M linhas. ### BUFFER LOAD - Cache Automático Para dimensões que raramente mudam, o Buffer cria um QVD automático e só recarrega quando o buffer expira. ``` // Recarrega da fonte apenas se o cache tiver mais de 7 dias Buffer (stale [7 days]) DimProduto: LOAD ProductID, ProductName, Category, SubCategory, UnitCost FROM [lib://MasterData/produtos.csv] (txt, utf8, embedded labels); ``` --- ## 3. Expressões e Visualizações ### Set Analysis vs IF() - A Diferença que Mais Impacta **IF() avalia condição linha por linha em toda a tabela.** Set Analysis filtra o conjunto antes da agregação - dramaticamente mais eficiente. ``` // Evitar: IF() linha por linha Sum(IF(Categoria = 'Eletrônicos', Valor, 0)) // Preferir: Set Analysis filtra antes de agregar Sum({} Valor) // Múltiplos filtros Sum({} Valor) ``` ### AGGR() - Quando Pré-Calcular no Script ``` // Pesado: recalcula a cada renderização do gráfico Avg(AGGR(Sum(Valor), ClienteID, MesAno)) // Eficiente: pré-calcular no script VendasMensaisCliente: LOAD ClienteID, MesAno, Sum(Valor) AS ValorMensal FROM vendas.qvd (qvd) GROUP BY ClienteID, MesAno; // No gráfico: simplesmente Avg(ValorMensal) ``` ### Variáveis para Expressões Reutilizadas ``` LET vVendasAno = "Sum({} Valor)"; LET vVendasAnoAnt = "Sum({} Valor)"; LET vCrescimento = "($(vVendasAno) - $(vVendasAnoAnt)) / $(vVendasAnoAnt)"; // Nos gráficos: $(vCrescimento) ``` --- ## 4. Checklist de Auditoria 1. Verificar synthetic keys no log de reload - resolver antes de qualquer outra otimização 2. Auditar campos com LOAD * - dropar o que não é usado em nenhum gráfico 3. Implementar camada QVD - obrigatório acima de 100k linhas com reload frequente 4. Substituir IF() por Set Analysis - revisar todos os KPIs e tabelas 5. Verificar número de objetos por sheet - máximo 8-10 objetos por página 6. Avaliar ODAG - se o dataset tem mais de 50M linhas, On-Demand App Generation é a arquitetura correta **Performance não é uma feature que se adiciona depois. É uma decisão de arquitetura que começa no modelo de dados.** Meça antes, otimize com dados, meça depois. Qual é o gargalo no seu app Qlik?
