01 — Diagnosis

The app works.
But for how long?

Most Qlik Sense environments I encounter at companies pass the visual test: nice dashboards, data that looks right, users navigating freely. But when you look under the hood, the story changes.

Scripts with no QVD layer. Reloads that pull 100% of source data every time. Unnecessary joins on the front-end. Section Access configured as an afterthought. These are apps that work until the day they stop working, and when they go down, nobody knows where to start.

💀

App that just barely runs

4-hour reloads. Full extract every night. A 2,000-line script with no comments. One developer who understands what's happening.

⚠️

Warning signs

Synthetic keys in the data model. Circular tables. Joins in the script that belong in the source. Engine RAM spiking on reload.

✅

Truly production-ready

Incremental reload in minutes. Separate QVD layers. Modular, documented scripts. Any developer can maintain it.

🚀

Built to scale

Granular Section Access. Performance monitoring. Versioned QVD layers. Data governance applied at the script level.

"A healthy Qlik app is not the one with the most charts. It is the one any developer can maintain two years from now."
02 — Architecture

The 3 layers that separate
juniors from seniors

Serious Qlik production environments follow a QVD layer architecture. It is the equivalent of the Medallion model (Bronze/Silver/Gold) that the Data Engineering world adopted, applied to the Qlik ecosystem.

🥉RAW
QVD

Layer 1: Raw Extraction

Exact copy of the source. No transformation. No join. No filter. This is your historical backup and source of truth. Never connect an app directly here.

🥈TRANSFORM
QVD

Layer 2: Transformation

Cleaning, typing, enrichment, and joins between entities. This is where business logic lives. Modular scripts, one file per entity.

🥇APP
QVD

Layer 3: Consumption App

Reads only transformed QVDs. Lean script, no business logic. Aggregations and Section Access filters. Reload in minutes, not hours.

01_RAW_Orders.qvs — Extraction Layer 
// ===============================================
// RAW LAYER: Pure extraction from source
// No transformation. No join. No filter.
// ===============================================

LET vQVDRaw   = 'lib://QVD/Raw/';
LET vQVDTF    = 'lib://QVD/Transform/';

Orders_RAW:
LOAD
    OrderID,
    CustomerID,
    OrderDate,
    Amount,
    Status,
    Now() AS _ExtractedAt
FROM [lib://DataSources/ERP_Orders.csv]
(txt, delimiter is ',', embedded labels);

STORE Orders_RAW INTO [$(vQVDRaw)Orders_RAW.qvd] (QVD);
DROP TABLE Orders_RAW;
03 — Performance

Incremental Load:
the end of full extract

If your script pulls 100% of source data on every reload, you are wasting resources, widening the failure window, and putting unnecessary pressure on transactional systems. Incremental Load fixes this by loading only new or modified records.

02_TF_Orders.qvs — Incremental Load with QVD 
// ===============================================
// INCREMENTAL LOAD: Delta only
// Compares QVD creation time with source
// ===============================================

// Get the timestamp from the last reload
IF NOT IsNull(QVDCreateTime('$(vQVDTF)Orders_TF.qvd')) THEN
    LET vLastLoad = QVDCreateTime('$(vQVDTF)Orders_TF.qvd');
ELSE
    LET vLastLoad = '1900-01-01'; // First run: full load
END IF

// Load existing records from QVD
Orders_TF:
LOAD *
FROM [$(vQVDTF)Orders_TF.qvd] (qvd)
WHERE OrderID NOT IN (
    SELECT OrderID FROM Orders WHERE ModifiedAt >= '$(vLastLoad)'
);

// Concatenate only the delta from source
CONCATENATE (Orders_TF)
SQL SELECT
    OrderID,
    CustomerID,
    CAST(OrderDate AS DATE)   AS OrderDate,
    Amount,
    UPPER(TRIM(Status))        AS Status
FROM dbo.Orders
WHERE ModifiedAt >= '$(vLastLoad)';

STORE Orders_TF INTO [$(vQVDTF)Orders_TF.qvd] (QVD);
DROP TABLE Orders_TF;
03_APP_Dashboard.qvs — Section Access 
// ===============================================
// SECTION ACCESS: Row-level security
// Always test in staging before production
// ===============================================

Section Access;
Access_Control:
LOAD * INLINE [
    ACCESS,   USERID,          REGION,    OMIT
    ADMIN,    DOMAIN\RAFAEL,   *,
    USER,     DOMAIN\ANA,      South,     Amount
    USER,     DOMAIN\CARLOS,   North,     Amount
    USER,     DOMAIN\LUCIA,    East,
];

Section Application;

// Load only transformed QVDs
Orders:
LOAD
    OrderID,
    CustomerID,
    OrderDate,
    Year(OrderDate)           AS Year,
    Month(OrderDate)          AS Month,
    Amount,
    Status,
    Region                     // Section Access control field
FROM [$(vQVDTF)Orders_TF.qvd] (qvd);
04 — Fatal Mistakes

The 5 mistakes that bring down
any Qlik environment

It does not matter the size of the company or how much was invested in licenses. These mistakes show up everywhere and all of them are preventable.

1

Untreated synthetic keys

When two tables share more than one field, Qlik automatically creates synthetic keys. They degrade performance and make the model unpredictable. Fix: rename conflicting fields or use explicit composite keys.

2

Full extract on million-row tables

Extracting 50 million records every night when only 0.1% changed is pure waste. Implement Incremental Load with a control field (ModifiedAt, RowVersion) and cut reload time by up to 95%.

3

Business logic on the front-end

KPIs calculated in complex Set Analysis expressions that should be pre-computed fields in the script. This multiplies processing for every chart object. Calculate in script, expose as a field.

4

Section Access without staging

Misconfigured Section Access in production can lock out all users instantly, including admins. Always test in a dev environment with real user accounts before promoting to production.

5

Monolithic scripts with no modularity

A 3,000-line script that does everything: extraction, transformation, joins, and load. Impossible to debug, impossible to maintain. Split by entity and centralize configuration in global variables.
