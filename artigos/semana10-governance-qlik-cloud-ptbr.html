Os 4 Pilares do Governance no Qlik Cloud

1
Estrutura de Espaços: a fundação de tudo

No Qlik Cloud, os espaços são a unidade fundamental de organização. Diferente do QlikView (onde pastas e seções de acesso controlavam tudo no servidor), aqui a lógica é baseada em quatro tipos de espaço com propósitos distintos.

👤
Espaço Pessoal
Cada usuário tem um. Uso para desenvolvimento individual e testes. Conteúdo não é compartilhado por padrão e não deve ir para produção.
🤝
Espaço Compartilhado
Colaboração entre equipes. Qualquer membro com permissão pode publicar e editar. Ideal para desenvolvimento colaborativo antes da publicação gerenciada.
🔒
Espaço Gerenciado
Produção. Apenas administradores do espaço publicam. Usuários comuns só consomem. Este é o destino final de todo conteúdo validado.
💾
Espaço de Dados
Para conexões de dados e pipelines. Separa a camada de dados das aplicações analíticas. Permite controle granular sobre quem cria e edita fontes de dados.
⚠️

Erro mais comum: usar apenas Espaços Compartilhados para tudo. Sem Espaços Gerenciados, não há controle sobre o que vai para produção. Qualquer desenvolvedor pode sobrescrever um app em uso pelos usuários finais.

2
Papéis e Permissões: quem pode fazer o quê

O Qlik Cloud opera com dois níveis de permissão: tenant-level (toda a plataforma) e space-level (dentro de cada espaço). Confundir esses dois níveis é a causa mais comum de problemas de acesso.

Papéis no nível do tenant (Management Console):

Tenant Admin
Controle total. Gerencia usuários, licenças, configurações e todos os espaços. Use com parcimônia.
Analytics Admin
Gerencia conteúdo analítico. Não acessa configurações de plataforma. Adequado para líderes técnicos de BI.
Developer
Cria apps e scripts. Pode criar espaços. Perfil padrão para analistas e desenvolvedores Qlik.
Analyzer
Consome dashboards. Não cria apps nem scripts. Ideal para usuários de negócio.

Papéis no nível do espaço:

  • ✓Owner: criador do espaço. Controle total sobre o espaço.
  • ✓Admin: gerencia membros e conteúdo do espaço. Pode publicar em Espaços Gerenciados.
  • ✓Contributor: cria e edita conteúdo (apenas em Espaços Compartilhados).
  • ✓Consumer: visualiza e interage com apps. Não edita.
  • ✓Data Consumer: acessa dados e conexões sem ver os apps analíticos.
Regra de ouro

Um usuário pode ser Developer no nível do tenant mas Consumer em um espaço específico. O nível do espaço sempre prevalece para aquele contexto. Isso permite controle granular sem criar perfis complexos no tenant.

3
Fluxo de Publicação: do desenvolvimento à produção

Um dos maiores erros em ambientes Qlik Cloud é não ter um fluxo claro de promoção de conteúdo. O resultado são apps de desenvolvimento acessíveis por usuários finais e apps de produção sendo editados diretamente.

👤 Espaço Pessoal (dev individual) ↓ revisão e aprovação 🤝 Espaço Compartilhado (homologação) ↓ validação técnica e de negócio 🔒 Espaço Gerenciado (produção) ↓ publicação controlada 👥 Usuários Finais (Consumers)

Nesse modelo, os usuários finais nunca têm acesso aos espaços de desenvolvimento. O conteúdo só chega a eles através do Espaço Gerenciado, garantindo que apenas versões validadas estejam disponíveis.

💡

Para ambientes com equipes maiores, considere criar Espaços Compartilhados por domínio de negócio (Financeiro, Comercial, Operações) e um único Espaço Gerenciado por domínio para produção. Evita o crescimento descontrolado de espaços.

4
Auditoria e Monitoramento: quem fez o quê e quando

O Qlik Cloud mantém logs de auditoria acessíveis pelo Management Console. Para ambientes enterprise, esses logs são fundamentais para compliance, rastreabilidade e resolução de incidentes.

O que o Activity Center registra:

  • ✓Criação, edição e exclusão de apps e fontes de dados
  • ✓Adição e remoção de membros de espaços
  • ✓Alterações de permissões no nível do tenant
  • ✓Execuções de cargas de dados (reloads) e falhas
  • ✓Acessos a aplicações (quem abriu, quando)
  • ✗Interações granulares dentro de um app (cliques, seleções): requer extensão customizada
Para compliance LGPD/GDPR

Os logs de auditoria do Qlik Cloud podem ser exportados via API para seu SIEM ou data lake. Estabeleça uma política de retenção e garanta que o time de segurança tenha acesso de leitura ao Management Console sem papel de Admin.

Os erros mais comuns e como evitá-los

  • ✗Dar papel de Tenant Admin para vários usuários: crie um grupo de Admin restrito e documente quem tem acesso e por quê.
  • ✗Criar um espaço por projeto ou por pessoa: organize por domínio de negócio, não por iniciativa. Espaços demais viram pesadelo de governança.
  • ✗Não ter Espaços Gerenciados: sem eles, não há separação real entre desenvolvimento e produção.
  • ✗Adicionar usuários diretamente nos espaços sem política de onboarding: use grupos de usuários (integração com IdP) em vez de gerenciar permissões individualmente.
  • ✗Ignorar os Espaços de Dados: misturar conexões de dados com apps analíticos dificulta o controle de quem acessa quais fontes.

Por onde começar: checklist de governance para novos tenants

  • ✓Definir os domínios de negócio que terão espaços (Financeiro, Comercial, RH, Operações)
  • ✓Criar pelo menos um Espaço Compartilhado e um Gerenciado por domínio
  • ✓Integrar o IdP corporativo (AD, Okta, Azure AD) para gestão de grupos
  • ✓Documentar a política de promoção de conteúdo (quem aprova a publicação em produção)
  • ✓Configurar alertas de auditoria para ações críticas (criação de Tenant Admin, remoção de espaços)
  • ✓Revisão trimestral de permissões e espaços órfãos
