Semana 8 · Qlik Cloud Migration

Os 5 Erros Mais Comuns na Migração para Qlik Cloud
(e Como Evitar Cada Um)

O que ninguém te conta antes de apertar o botão de migrar

Já acompanhei dezenas de projetos de migração para o Qlik Cloud. Os bem-sucedidos não foram os que tinham mais orçamento. Foram os que conheciam as armadilhas antes de cair nelas. Aqui estão os cinco erros que aparecem em praticamente todo projeto, com o que fazer para não cometê-los.

67% dos projetos excedem o prazo original
3x mais chamados de suporte no primeiro mês pós-migração
40% dos retrabalhos causados por modelo de dados não auditado

Estimativas baseadas em projetos acompanhados em campo 2023-2024

Os 5 Erros

1
Migrar sem auditar o modelo de dados primeiro

O QlikView acumula anos de patches, campos duplicados, QVDs obsoletos e joins que "ninguém sabe por que existem, mas ninguém remove". Levar essa dívida técnica para o Qlik Cloud não limpa o problema, multiplica ele. Você gasta o mesmo esforço de migração e chega do outro lado com as mesmas anomalias, agora em uma plataforma nova.

⚠️

Campos sem uso consomem memória e aumentam o custo da licença no modelo SaaS do Qlik Cloud. Cada campo desnecessário tem preço.

Como evitar

Faça um QlikView Audit antes de iniciar a migração. Liste todas as tabelas, campos e QVDs. Documente quem usa o quê. Elimine o que não tem dono. Chegue no Qlik Cloud com um modelo 30% mais enxuto do que o original.

2
Fazer Big Bang: migrar tudo de uma vez

A pressão do projeto leva muitas equipes a tentar mover todos os apps de uma só vez. Parece eficiente no papel. Na prática, quando algo quebra, você não sabe o que causou o problema porque mudou tudo ao mesmo tempo. O rollback vira um pesadelo.

Abordagem recomendada: migração em waves
Wave 1 (Semanas 1-4):
  - Apps de menor criticidade
  - Valida ambiente, permissões, conectores
  - Treina a equipe técnica no novo ambiente

Wave 2 (Semanas 5-10):
  - Apps operacionais de média criticidade
  - Ajusta padrões de load script para Qlik Cloud
  - Valida performance das queries

Wave 3 (Semanas 11-16):
  - Apps críticos de produção (BI financeiro, dashboards executivos)
  - Parallel run: QlikView e Qlik Cloud lado a lado
  - Validação de KPIs antes do switch definitivo
Como evitar

Segmente a migração em waves por criticidade. Comece sempre pelo que dói menos se quebrar. Use o parallel run para validar KPIs críticos antes de desligar o QlikView.

3
Ignorar as diferenças de Set Analysis entre QlikView e Qlik Cloud

Esse é o erro mais técnico e um dos mais perigosos. Algumas expressões de Set Analysis se comportam de forma diferente no Qlik Sense e no Qlik Cloud, especialmente quando envolvem flags calculados, alternate states e expressões dentro de sets. KPIs críticos podem trazer números errados sem dar nenhum erro visível.

Exemplo de expressão que pode variar
// QlikView: funciona como esperado em muitos contextos
Sum({<Ano={$(=Max(Ano))}>} Receita)

// Qlik Cloud / Qlik Sense: mesma expressão, mesma intenção,
// mas o comportamento de Dollar Sign Expansion dentro
// do Set pode divergir dependendo do contexto do objeto.
// Sempre valide com dados reais antes de ir para produção.
Como evitar

Crie um catálogo de expressões críticas antes de migrar. Para cada KPI importante, documente o valor esperado com dados de teste. Depois da migração, rode uma bateria de validação comparando QlikView vs. Qlik Cloud com o mesmo conjunto de dados.

4
Esquecer o change management dos usuários finais

A equipe técnica migra os apps. Os usuários abrem o Qlik Cloud pela primeira vez e não reconhecem nada. A interface mudou, o menu sumiu, o botão que sempre usavam para exportar agora fica em outro lugar. O resultado previsível: resistência, chamados de suporte e pedidos para "voltar para o antigo".

Migração de ferramenta sem migração de cultura é meio projeto. A segunda metade será a mais cara.

Como evitar

Planeje pelo menos quatro semanas de comunicação antes do switch. Faça sessões de treinamento segmentadas por perfil de usuário (consumidor, autor, administrador). Crie um guia rápido de "o que mudou e onde encontrar". Designe champions dentro de cada área de negócio.

5
Subestimar o impacto das extensões customizadas

Extensões desenvolvidas para QlikView ou Qlik Sense on-premise frequentemente não funcionam no Qlik Cloud. As restrições de segurança do ambiente SaaS são mais rígidas, a API mudou em várias versões, e algumas extensões dependem de recursos que simplesmente não existem mais.

Descobrir isso na semana do go-live é a receita para atrasar o projeto em pelo menos um mês.

Como evitar

Inventarie todas as extensões customizadas no início do projeto. Para cada uma: teste no ambiente Qlik Cloud, documente o que funciona e o que quebra. Avalie se substitui por um visual nativo equivalente, reescreve a extensão para o novo padrão ou elimina. Reserve pelo menos quatro semanas para isso no cronograma.

O padrão que une todos os cinco erros

Olhando os cinco juntos, o padrão é o mesmo: todos são problemas de planejamento insuficiente, não de capacidade técnica. A equipe sabe migrar. O que falta é descobrir as armadilhas antes de tropeçar nelas.

Projetos de migração bem-sucedidos investem de 30% a 40% do cronograma total em preparação antes de mover o primeiro app. Parece muito. Mas é menos do que o retrabalho que vem depois quando você pula essa etapa.

A migração para o Qlik Cloud é inevitável. O QlikView está em fim de vida. O NPrinting SaaS já tem data de obrigatoriedade. O caminho não é se você vai migrar, é como você vai fazer isso sem transformar o projeto em uma crise.
