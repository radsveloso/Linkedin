Anúncio de GA

O Qlik anunciou a disponibilidade geral (GA) das capacidades de agentic data engineering no Qlik Cloud em 30 de junho de 2026. A novidade está disponível no Qlik Talend Cloud e no Qlik Cloud Analytics. Os primeiros artigos técnicos em PT-BR sobre isso aparecem agora.

O que o Qlik chama de "agentic"

Antes de entrar no código, vale alinhar o vocabulário. O Qlik não criou um chatbot de dados com acesso ao seu app. Criou quatro agentes especializados, cada um com escopo definido, disponíveis via interface conversacional e via protocolo MCP (Model Context Protocol).

A diferença importa: um chatbot responde perguntas. Um agente executa tarefas, mantém contexto entre etapas e pode ser orquestrado por outros sistemas. É essa distinção que muda o workflow do dev sênior.

Pipelines Declarativos: a maior mudança para engenheiros

Esta é a funcionalidade que mais impacta quem trabalha diariamente com Load Script. Vale entender a diferença conceitual antes de avaliar quando usar.

O Load Script tradicional é imperativo: você especifica passo a passo como transformar e carregar cada tabela. O pipeline declarativo é um contrato: você define o que quer que exista, e o sistema decide como gerar, otimizar e manter.

Antes: Load Script imperativo
  • Você escreve cada passo
  • Ordem de LOAD importa para associações
  • Refatoração exige reescrita manual
  • Documentação separada do código
  • Difícil de versionar como contrato
Depois: Pipeline Declarativo
  • Você define o que quer
  • Contrato estável e versionável
  • Agente gera e refatora automaticamente
  • Documentação embutida na especificação
  • Compatível com agentes de código externos
Ponto técnico

O Load Script não desapareceu. Pipelines declarativos coexistem com scripts existentes. A lógica complexa de negócio, o modelo associativo do Qlik e as transformações avançadas com Set Analysis continuam sendo responsabilidade do engenheiro. O que o agente assume é a geração e manutenção do boilerplate de ingestão e transformação padrão.

Exemplo: ingestão tradicional vs. declarativa

Um cenário comum: carregar pedidos de um QVD com formatação regional e filtro de data.

QVS · Load Script (modo imperativo) OrdersFact.qvs 
// Abordagem tradicional: você escreve cada linha
OrdersFact:
LOAD
    OrderID,
    CustomerID,
    Date(OrderDate, 'YYYY-MM-DD') as OrderDate,
    Num(TotalAmount, 'R$ #.##0,00') as TotalAmount,
    ProductID,
    StatusCode
FROM [lib://DataLake/orders.qvd] (qvd)
WHERE Year(OrderDate) >= 2024;

// Problema: qualquer mudança de schema exige reescrita manual
// Sem documentação sobre a intenção, só sobre a execução
Prompt para o Agente de Pipeline via chat ou MCP 
// Você descreve a intenção; o agente gera a especificação declarativa
// e o script otimizado a partir dela

"Crie um pipeline para a tabela OrdersFact com as seguintes regras:
 - Fonte: QVD em lib://DataLake/orders.qvd
 - Formatar OrderDate como YYYY-MM-DD
 - Formatar TotalAmount como moeda BRL
 - Filtrar apenas registros de 2024 em diante
 - CustomerID é chave de join com CustomersDim
 - Freshness SLO: dados disponíveis até as 06h de cada dia"

// Resultado: especificação versionável + script gerado + regra de qualidade
// Quando o schema da fonte muda, o agente refatora o script mantendo o contrato

MCP Integration: Qlik com Claude Code ou GitHub Copilot

Esta é a parte que mais vai interessar devs que já usam ferramentas de IA no workflow diário. O Qlik disponibilizou ferramentas MCP que permitem configurar qualquer agente de codificação compatível, incluindo Claude Code e GitHub Copilot, para interagir diretamente com o Qlik Cloud.

Isso significa que você pode usar o agente de codificação que já está aprovado pela sua empresa para construir pipelines, gerenciar Data Products e consultar o catálogo do Qlik sem abrir outra interface.

JSON · Configuração MCP claude_desktop_config.json 
{
  "mcpServers": {
    "qlik-cloud": {
      "command": "npx",
      "args": ["@qlik/mcp-server"],
      "env": {
        "QLIK_HOST": "seu-tenant.us.qlikcloud.com",
        "QLIK_CLIENT_ID": "seu-oauth-client-id",
        "QLIK_CLIENT_SECRET": "seu-client-secret"
      }
    }
  }
}

Com a configuração ativa, você passa a poder pedir ao agente diretamente no seu editor:

Exemplos de prompts via MCP 
// Auditoria de qualidade
"Liste todos os Data Products com trust score abaixo de 80%"

// Criação de regra de qualidade
"Crie uma regra de qualidade para garantir que OrderDate
 nunca seja nulo na tabela OrdersFact"

// Geração de pipeline
"Gere o pipeline declarativo para carregar a tabela Customers
 do Snowflake para o DataLake do Qlik, com SLO de freshness
 de 4 horas e detecção automática de duplicatas"

// Exploração de catálogo
"Quais tabelas no catálogo contêm dados de transação financeira
 e têm documentação de glossário incompleta?"
O que isso representa na prática

O workflow muda de: abrir o Qlik Hub, navegar para Data Integration, criar pipeline manualmente, voltar para o editor para integrar. Para: descrever o que precisa no seu editor e receber o pipeline gerado com SLO e documentação. A mudança é no custo de contexto, não na capacidade técnica.

Data Quality com SLOs: dados com contrato de nível de serviço

O conceito de SLO (Service Level Objective) veio do mundo de engenharia de software (SRE) e o Qlik o trouxe para dados. Em vez de verificações de qualidade manuais e esporádicas, você define contratos de qualidade que são monitorados continuamente.

O agente de Data Quality permite criar esses contratos via linguagem natural e os trust scores resultantes aparecem diretamente nos apps Qlik para os usuarios finais.

Exemplo: SLO via agente 
// Definição de SLO para a tabela OrdersFact
"Defina um SLO para OrdersFact com os seguintes critérios:
 - Completude de OrderDate: >= 99.5%
 - Unicidade de OrderID: 100%
 - Freshness: dados do dia disponíveis até 06h AM (fuso BRT)
 - TotalAmount não pode ser negativo: 100%
 - CustomerID deve existir em CustomersDim: >= 99%"

// O agente:
// 1. Cria as regras de qualidade
// 2. Agenda a verificacao automatica
// 3. Calcula o trust score composto
// 4. Configura alertas quando SLO é violado
// 5. Expoe o trust score no app Qlik

Por que isso importa para devs sênior

Antes, um trust score era um número que você inventava ou calculava manualmente. Agora ele é um contrato auditável, com histórico de violações e responsável definido. O usuário que vê o gráfico também vê o score de confiança dos dados que está analisando.

Para times que atendem áreas reguladas (financeiro, saúde, compliance), isso deixa de ser um diferencial e passa a ser obrigatório nos próximos 12 a 24 meses.

O ponto que ninguem fala

Toda vez que uma plataforma lança IA para engenharia de dados, a discussão migra para "o engenheiro vai ser substituído?". Essa não é a pergunta certa.

O que os agentes eliminam vs. o que continuam sendo sua responsabilidade

Agentes assumem

  • Boilerplate de ingestão e carga padrão
  • Catalogação e documentação de ativos
  • Criação de regras de qualidade repetitivas
  • Detecção de anomalias em pipelines
  • Geração de especificações declarativas
  • Refatoração ao mudar schema de fonte

Você continua sendo responsável

  • Modelagem do modelo associativo Qlik
  • Lógica complexa de negócio no script
  • Set Analysis para métricas específicas
  • Estratégia de QVD layers e incremental
  • Section Access e governança de acesso
  • Conhecimento do domínio de negócio

O dev sênior que já entende o modelo associativo do Qlik se torna mais produtivo com agentes. O dev que ainda não entende vai criar problemas mais rápido, porque o agente vai gerar código sem o contexto de como o Qlik associa dados na memória.

A curva de aprendizado não desapareceu. Ela se deslocou: de "como escrever o script" para "como especificar bem o que o agente deve gerar".

Recomendação prática

Se você já tem Qlik Talend Cloud ou Qlik Cloud Analytics Enterprise, comece pelo agente de Data Quality. É o que tem ROI mais rápido: você vê os trust scores aparecendo nos apps e o time de negócio percebe a diferença em dias, não em meses. Os pipelines declarativos exigem mais planejamento de especificação para dar resultado consistente.

Próximo passo para devs sênior

O roteiro para quem quer estar na frente da curva nos próximos seis meses:

1. Configurar o MCP do Qlik no seu agente de codificação. Isso já está disponível e não exige mudança de licença se você já tem Qlik Cloud Analytics. É o ponto de entrada mais rápido.

2. Mapear quais pipelines de ingestão são candidatos para declarativos. Ingestão simples de fontes estruturadas, sem lógica de negócio complexa, são os melhores candidatos. Scripts com transformação pesada de negócio continuam sendo código manual por ora.

3. Definir os primeiros SLOs para as tabelas mais críticas. Identifique as três tabelas que o negócio mais usa e defina contratos de qualidade explícitos. Isso cria evidência auditável e visibilidade para o usuário final.
