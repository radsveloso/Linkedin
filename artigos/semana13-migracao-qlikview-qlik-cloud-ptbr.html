Migração QlikView para Qlik Cloud:
as armadilhas que ninguém te conta

O guia honesto para gestores e desenvolvedores sobre o que realmente falha e como evitar retrabalho de meses

por Rafael Veloso Setembro 2026 Leitura: ~9 min

"Migrar QlikView para Qlik Cloud não é upgrade: é uma mudança de paradigma. Quem trata como upgrade paga o preço meses depois."

Em 2026, a maioria das grandes empresas que ainda opera QlikView está em algum estágio de migração para o Qlik Cloud. Algumas já concluíram. Muitas estão no meio do caminho. E boa parte está descobrindo agora o que deveria ter planejado antes de começar.

Neste artigo, vou abordar as armadilhas mais comuns dessa jornada, com dois ângulos deliberadamente distintos: o do gestor que aprova o projeto e o do desenvolvedor que executa. Porque os dois sofrem por razões diferentes.

O cenário: Uma migração que saiu do controle

Caso referência (fictício, baseado em padrões reais)

Uma empresa de médio porte com 12 anos de QlikView decide migrar para o Qlik Cloud. O projeto é aprovado com estimativa de 4 meses e orçamento para 2 desenvolvedores em tempo parcial.

Seis meses depois: 40% dos relatórios estão migrados, os 60% restantes têm complexidade muito maior do que o previsto, o modelo de dados principal foi refeito duas vezes, e a área financeira ainda usa o QlikView porque "não está confiando nos números novos".

O que errou? Não foi falta de competência técnica. Foi falta de mapeamento das diferenças reais entre as duas plataformas, e das expectativas não alinhadas entre gestor e equipe técnica.

Visão do Gestor: O que o projeto não vai te contar

Se você é o responsável pela aprovação e acompanhamento da migração, estas são as armadilhas que vão aparecer no seu radar, geralmente tarde demais.

  • Estimativa baseada em quantidade de relatórios, não em complexidade

    O time diz "temos 80 relatórios para migrar". Isso não significa absolutamente nada sem saber quantos usam scripts QVD complexos, loops aninhados, macros VBScript ou seções de acesso. Um relatório pode levar 2 horas ou 3 semanas.

    Exija um inventário técnico antes da estimativa. Classifique os apps em baixa, média e alta complexidade com critérios objetivos.

  • O modelo de dados não é portável como parece

    Gestores assumem que o modelo de dados do QlikView "vem junto". Na prática, a arquitetura de Spaces, Shared Data e Data Files do Qlik Cloud muda onde e como os dados são armazenados e acessados. Dados que antes ficavam em QVDs locais precisam ir para um storage centralizado, e isso tem impacto em governança e licença.

    Inclua no escopo a redesign do modelo de dados, não apenas a migração de scripts. Reserve pelo menos 20% do orçamento total para isso.

  • Seção de Acesso (Section Access) vira dor de cabeça de segurança

    O controle de acesso por dados que funcionava no QlikView precisa ser repensado no Qlik Cloud. As regras de Section Access continuam existindo, mas a integração com SSO, grupos do Azure AD e permissões de Space adiciona camadas que o projeto original raramente contempla.

    Mapeie todos os grupos de acesso e regras existentes antes de iniciar. Envolva o time de segurança/TI desde o dia 1, não na semana de go-live.

  • O usuário final vai rejeitar a interface nova

    O Qlik Sense (base do Qlik Cloud) tem uma experiência visual diferente do QlikView. Usuários acostumados há anos com o layout antigo vão reclamar, independentemente de a nova versão ser melhor. Sem gestão de mudança, a adoção falha mesmo com a migração técnica concluída.

    Conduza sessões de validação com usuários-chave durante o desenvolvimento. Não apresente só no go-live. Invista em treinamento e comunicação.

  • Licença e custo de consumo no Qlik Cloud surpreendem

    O modelo de licenciamento do Qlik Cloud é diferente do QlikView. Capacidade de reload, armazenamento de dados e número de apps podem gerar custos não previstos no orçamento inicial, especialmente em ambientes com muitos reloads agendados ou grandes volumes de dados.

    Solicite uma análise de consumo estimado antes de fechar o contrato. Use o ambiente de trial para medir uso real com os apps mais pesados.

Visão do Desenvolvedor: Onde o script QlikView para de funcionar

Se você é quem vai colocar a mão no código, aqui estão as diferenças técnicas que mais geram retrabalho, com exemplos práticos de como contornar cada uma.

Armadilha 1: Macros VBScript não existem no Qlik Cloud

No QlikView, macros VBScript eram amplamente usadas para automação: abrir/fechar apps, navegar entre sheets, manipular seleções programaticamente. No Qlik Cloud, VBScript não existe. Ponto.

Impacto real: Apps com muitas macros precisam ter toda a lógica de automação reescrita usando Application Automation (ferramenta nativa do Qlik Cloud) ou APIs REST. Isso não é refatoração: é uma reconstrução completa.

QlikView - Macro VBScript (não funciona no Cloud)
' Exemplo de macro QlikView que NÃO migra
Sub AbrirApp()
    Set oApp = ActiveDocument
    oApp.GetField("Ano").Select("2024")
    oApp.Reload
    MsgBox "Reload concluído!"
End Sub
Qlik Cloud - Alternativa via Application Automation
// No Qlik Cloud, use Application Automation (sem código)
// ou a API REST para automações equivalentes

// Exemplo via API REST - selecionar valor e recarregar
POST /v1/apps/{appId}/actions/apply-bookmark
{
  "bookmarkId": "seu-bookmark-id"
}

// Para reload via API:
POST /v1/reloads
{
  "appId": "seu-app-id",
  "partial": false
}

Armadilha 2: Loops e Sub-rotinas no Load Script têm comportamento diferente

Scripts com For Each, Do While e chamadas a Sub dentro do Load Script funcionam no QlikView mas podem se comportar de forma inesperada no Qlik Cloud, especialmente quando dependem de variáveis de ambiente ou caminhos de arquivo locais.

QlikView - Loop com caminho local (quebra no Cloud)
// Padrão QlikView que FALHA no Qlik Cloud
For Each vFile in FileList('C:\Dados\Vendas\*.qvd')
    LOAD * FROM [$(vFile)] (qvd);
Next vFile
Qlik Cloud - Padrão correto com Data Files
// No Qlik Cloud, arquivos ficam em Data Files ou conexão
// Use a lib de conexão configurada no Space

For Each vFile in FileList('lib://DataFiles/Vendas/*.qvd')
    LOAD * FROM [$(vFile)] (qvd);
Next vFile

// Ou use uma conexão de dados configurada:
LOAD * FROM [lib://MinhaConexao:DataFiles/Vendas/vendas_2024.qvd] (qvd);

Armadilha 3: Section Access com grupos do AD quebra silenciosamente

A integração de Section Access com grupos do Azure Active Directory no Qlik Cloud exige configuração específica no tenant. Se não estiver configurada corretamente, a tabela de segurança simplesmente não filtra, e o usuário vê tudo, sem erro visível.

Cuidado crítico: Nunca publique um app com Section Access em produção sem validar com usuários de diferentes perfis de acesso. O comportamento silencioso (sem erro) é a armadilha mais perigosa desta migração.

Qlik Cloud - Section Access com grupo AD
Section Access;
LOAD * INLINE [
    ACCESS,  USERID,           REGION
    ADMIN,   DOMAIN\adm_bi,    *
    USER,    %grp_vendas_sul,  Sul
    USER,    %grp_vendas_norte,Norte
];
// Prefixo % identifica grupos AD (não usuários individuais)
// Requer configuração do IdP no Qlik Cloud Management Console

Section Application;
LOAD
    Data,
    Vendas,
    Region,
    // ... demais campos
FROM [lib://DataFiles/vendas.qvd] (qvd)
WHERE EXISTS(REGION, Region);

Armadilha 4: Agendamento de reload muda completamente

No QlikView, os reloads eram agendados pelo QlikView Server (QVS) com tarefas no Publisher. No Qlik Cloud, o agendamento é por app, dentro da plataforma, e tem limitações de horário e frequência dependendo da licença contratada.

Funcionalidade QlikView Publisher Qlik Cloud
Agendamento Por tarefa, com dependências Por app, cron ou trigger de evento
Reload encadeado Nativo (tarefa A dispara tarefa B) Requer Application Automation
Reload condicional Via script ou trigger customizado Application Automation com condições
Notificação de falha Email via Publisher Automation + webhook/email
Log de execução Arquivo de log local Console de monitoramento centralizado

Armadilha 5: Set Analysis com variáveis de sessão

Set Analysis que usa variáveis calculadas em tempo de sessão pode se comportar de forma diferente no Qlik Cloud, especialmente quando as variáveis são definidas via macro ou carregadas de forma dinâmica.

Padrão que pode falhar - variável calculada em Set Analysis
// No QlikView, variáveis definidas por macro eram usadas assim:
Sum({$<Ano={$(=vAnoAtual)}>} Vendas)

// No Qlik Cloud, sem macros, vAnoAtual precisa ser
// carregada via Load Script ou definida na UI:
Let vAnoAtual = Year(Today());

// Ou use expressões diretas no Set Analysis:
Sum({$<Ano={$(=Year(Today()))}>} Vendas)

// Crie FlagAnoAtual=1 no QVD e filtre por ele

Checklist: Antes de iniciar a migração

Para o Gestor

☐ Inventário técnico com classificação de complexidade
☐ Mapeamento de usuários e perfis de acesso
☐ Plano de gestão de mudança e treinamento
☐ Análise de licença e estimativa de consumo
☐ Critérios claros de aceite por relatório
☐ Período de coexistência QlikView + Cloud definido
☐ Comunicação com as áreas usuárias antes do go-live

Para o Desenvolvedor

☐ Mapeamento de todas as macros VBScript existentes
☐ Auditoria de Section Access e grupos de acesso
☐ Revisão de todos os caminhos de arquivo (FileList, QVDs)
☐ Teste de Set Analysis com variáveis dinâmicas
☐ Validação de reloads agendados e dependências
☐ Ambiente de dev/test separado do produção no Cloud
☐ Teste de Section Access com usuários reais antes do go-live

Conclusão

A migração de QlikView para Qlik Cloud vale a pena. A plataforma nova é genuinamente mais poderosa, colaborativa e escalável. Mas o caminho até lá tem armadilhas reais que não aparecem nos materiais de marketing..

O gestor que entende onde estão os riscos técnicos consegue planejar o projeto com realismo. O desenvolvedor que conhece as diferenças de plataforma evita retrabalho de semanas. Juntos, eles fazem uma migração que chega ao go-live sem surpresas desagradáveis.

  • Trate a migração como um projeto de redesign, não apenas de portabilidade
  • Mapeie macros, Section Access e loops antes de qualquer estimativa
  • Envolva usuários-chave desde o início, não só no go-live
  • Valide o Section Access com usuários reais antes de desligar o QlikView
  • Planeje um período de coexistência das duas plataformas
